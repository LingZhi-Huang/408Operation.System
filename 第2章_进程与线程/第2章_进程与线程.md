### 一个贯穿全章的比喻：餐厅里的"订单"

把操作系统想象成一家餐厅的后厨：

| 概念 | 比喻 | 说明 |
| --- | --- | --- |
| **程序** | 菜单（菜谱） | 永远躺在纸上，**一动不动**，是静态的。同一个菜谱可以印很多份 |
| **进程** | 一份正在被做的**订单** | 是"执行中的程序"，有出生（下单）、有死亡（上菜），是**动态**的 |
| **PCB** | 订**单小票** | 记录这张订单的所有信息（客人是谁、点了什么、做到哪一步），**挂在后厨墙上（常驻内存）**，是整个后厨管理订单的依据 |
| **就绪队列** | 等下单的后厨窗口 | 订单下达后排队等待厨师（CPU）去做 |
| **运行** | 厨师正在做这道菜 | 同一时刻一名厨师只能做一道菜（单核 CPU） |
| **阻塞** | 缺原料、等着配送员送菜 | 菜做到一半缺原料了，只能停下等原料，此时厨师去做别人的菜 |
| **调度** | 厨师挑下一张单子 | 从等单窗口里选下一张单（FCFS / 短单优先 / 张三优先 / 轮流做） |
| **同步/互斥** | 两个厨师抢同一口锅、同一把刀 | 锅不能两个人同时用（互斥）；先放肉才能炒（同步） |
| **死锁** | 两人各拿一根筷子，谁都不肯放下 | 谁都吃不上饭，必须有人让步 |

> 【记忆口诀】**程序是菜单，进程是订单，PCB 是小票，状态是 "创建→就绪→运行→阻塞/终止" 的循环。**

# 2.1 进程的概念、组成与特征

## 2.1.1 为什么要引入"进程"？——并发程序的三个特点

在单道程序（一次只跑一个程序）的年代，程序就是"顺序执行"：甲跑完才轮到乙，CPU 利用率低、环境简单。后来出现了**多道程序设计**：多个程序**同时驻留内存、交替执行**（宏观上同时，微观上交替）。这一下就出了问题——程序并发执行产生了三个特点：

1. **间断性**：CPU 被多个程序轮流使用，一个程序"走走停停"（时间片用完被抢走、请求 I/O 被阻塞），不再是连续执行。
2. **失去封闭性**：多个程序共享变量、缓冲区、打印机等资源，A 改的变量 B 也可能在改，程序的执行环境不再是"封闭"的，彼此会**互相影响**。
3. **不可再现性**：由于间断与共享，同样输入的两次运行，**运算结果可能与时间、速度有关**，甚至不完全一样。

> 【考点】三者关系常考：**间断性、失去封闭性、不可再现性** 是程序并发执行的三个特点，正是这三点导致了"程序"这个概念**不再合适**——程序是静态的，无法描述"执行到哪一步、占用了什么资源"。于是引入 **进程**，用 PCB 把"当前运行现场"记录下来，使并发执行可管理、可复现。

## 2.1.2 进程的定义

**进程（Process）** 是 **进程实体（Process Image，也叫进程映像）的运行过程**，是**系统进行资源分配和调度的一个独立单位**。

- 核心：**进程是程序的"一次"执行过程**——同一个程序可以被执行多次，形成多个进程。
- 静态与动态：**程序是静态的（菜谱），进程是动态的（做菜过程）**。

> 【易错】① 程序 = 代码实体（静态），进程 = 代码 + 运行状态（动态）。② **一个程序可以对应多个进程**（例如同一个浏览器程序的多个标签页，在 Windows 中往往共享同一份程序段，却是多个进程）；**一个进程一般只关联一段程序**，但进程的执行过程是动态变化的。③ 进程具有生命周期：创建→运行→消亡，**进程是短暂的，程序是永久的**。

*图2-27 程序 vs 进程：磁盘上的程序文件是"菜谱"；内存里每个带着 PCB 的执行实例是"正在炒的那盘菜"。同一份菜谱可以同时炒三盘。*

**图后解读要点**：

- **"一个程序多个进程"的考研变体**：判断题"进程与程序一一对应" → **错**；选择题"打开 3 次同一应用，系统中有几个进程/几份程序" → **3 个进程、通常 1 份只读程序段（代码可共享）**；
- **"程序是进程的组成部分"也对**：进程实体 = PCB + 程序段 + 数据段——所以"程序段是进程实体的组成部分"这句话正确；但"进程是程序的组成部分"就反了。

## 2.1.3 进程的组成：PCB + 程序段 + 数据段

进程实体由三部分组成，常统称 **进程映像**：

![2-1 进程实体组成](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-01_process_entity.png)

*图2-1 进程实体 = PCB（常驻内存）+ 程序段（代码）+ 数据段（运行数据）。PCB 是进程存在的唯一标志。*

| 组成 | 内容 | 备注 |
| --- | --- | --- |
| **PCB**（进程控制块） | 描述进程的所有管理信息 | **常驻内存**；进程存在的**唯一标志**；没有了 PCB，进程就不存在了 |
| **程序段** | 程序的代码（指令序列） | 可执行；**可被多个进程共享**（如多个浏览器进程共享同一段代码） |
| **数据段** | 运行时数据（全局变量、局部变量等） | 每个进程独立（各自的数据互不干扰） |

【考点】"PCB 与程序段、数据段是否可以交换到外存？"——**程序段和数据段**（用户空间的代码和数据）**可以被换出**（比如挂起、页面置换）；但 **PCB 常驻内存**，因为操作系统要时刻管理进程，PCB 没了进程就"找不到了"。

### PCB（进程控制块）详解——本章"毛细血管级"考点

PCB 中存放的内容可以分成四大区：

![2-2 PCB 的内容（四个分区）](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-02_pcb_structure.png)

*图2-2 PCB 四分区：进程描述信息、进程控制和管理信息、资源分配清单、处理机现场信息（CPU 现场）。*

| 分区 | 主要内容 | 常考点 |
| --- | --- | --- |
| ① **进程描述信息** | 进程标识符 **PID**（唯一）、用户标识符 UID、家族关系（父/子进程指针） | PID 是**进程唯一**标识；父子进程通过指针串起来 |
| ② **进程控制和管理信息** | 当前状态（就绪/运行/阻塞…）、优先级、时间片、已运行时间、等待时间 | 状态、优先级是**调度**的依据 |
| ③ **资源分配清单** | 程序段指针、数据段指针、已打开文件（文件描述符表）、已分配的设备/资源 | "进程拥有哪些资源"查这里——**银行家算法**里进程的 Allocation 就源于此 |
| ④ **处理机现场信息** | 通用寄存器组的值、程序计数器 **PC**、程序状态字 **PSW**、栈指针 | **切换进程时保存/恢复的就是这些**；这就是"现场" |

PCB 的组织方式有**链表方式**（同一状态的进程用指针串成就绪队列、阻塞队列、终止队列——**教科书与真题默认**）和**索引方式**（按状态建索引表，效率更高）。

> 【考点】"PCB 是进程存在的唯一标志"——进程状态转换的本质就是**修改 PCB 里的状态字段**；调度就是**选出 PCB、把 CPU 现场换成它的现场**。所以**没有 PCB 就没有进程**。

## 2.1.4 进程的特征

1. **动态性**——进程是程序的**一次执行**，有生命周期（创建→运行→终止）。**动态性是进程最基本的特征**。
2. **并发性**——多个进程可以同时存在、交替运行。
3. **独立性**——进程是**资源分配**和**获取处理机调度**的**两个基本单位**，各进程的地址空间相互独立。
4. **异步性**——各进程按各自**不可预知的速度**推进（走走停停），所以同步手段是必需的。
5. **结构性**——进程由 **PCB + 程序段 + 数据段** 组成。

> 【记忆口诀】**"动并独异构"**：动态（最基本）、并发、独立、异步、结构。

> 【易错】不要混淆"进程是系统进行资源分配的基本单位"这句话——**引入线程后**，准确的表述是：**进程是资源分配的基本单位，线程是处理机调度的基本单位**（详见 2.5）。

# 2.2 进程的状态与转换

## 2.2.1 进程的三种基本状态（先记三个）

1. **运行态（Running）**：正在 CPU 上执行（**单 CPU 同一时刻最多一个**；多核则多个）。
2. **就绪态（Ready）**：万事俱备（已获得除 CPU 以外的一切资源），**只差 CPU**，排队等待调度。
3. **阻塞态（Blocked，也叫等待态）**：正在等待某事件（I/O 完成、等待其他进程给信号），**即使 CPU 空了也不能运行**。

> 【记忆口诀】**"就绪 = 万事俱备只欠 CPU；阻塞 = 事件没到，给了 CPU 也没用"**。

## 2.2.2 进程五状态模型（必考：六条边、各边"为什么"与"谁发起"）

加上**创建态**和**终止态**，就是完整五状态模型：

![2-3 进程五状态模型](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-03_five_states.png)

*图2-3 进程五状态模型。每一条转换边都要记住两件事：① 触发原因；② 是进程自己主动请求，还是由 OS/硬件施加（被动）。*

**五状态**含义：

| 状态 | 含义 | 说明 |
| --- | --- | --- |
| 创建态（New） | 正在创建：申请空白 PCB → 分配内存等资源 → 初始化 PCB → 插入就绪队列 | **创建完成后进就绪队列**（不是直接运行！） |
| 就绪态 | 万事俱备，只等 CPU | 排在就绪队列中 |
| 运行态 | 正在使用 CPU | 单 CPU 同时只有一个 |
| 阻塞态 | 等事件（I/O、信号） | 主动等待 |
| 终止态（Terminated） | 进程结束：回收资源、撤销 PCB | **PCB 被删除后进程实体就不存在了** |

**六条转换边**（每条都要按"触发原因 + 主动/被动"两维记忆）：

| 编号 | 转换 | 触发原因 | 谁主动 | 一句话记忆 |
| --- | --- | --- | --- | --- |
| ① | 创建 → 就绪 | 创建完成（分配资源、初始化 PCB 完成，放入就绪队列） | **被动**（OS 执行创建原语的结果） | 创建好就直接排队，不直接上 CPU |
| ② | 就绪 → 运行 | 被调度选中，获得 CPU | **被动**（进程自己是无法"决定"上CPU的，必须被选中） | "被动"二字是 408 最爱挖的坑 |
| ③ | 运行 → 就绪 | 时间片用完；或被更高优先级进程抢占 | **被动**（被 OS 剥夺！） | 注意：**是"时间片用完"导致被抢，不是进程主动让** |
| ④ | 运行 → 阻塞 | 请求 I/O；等待某事件（如等待信号量、等待缓冲区） | **主动**（进程自己请求的） | **"运行→阻塞"是唯一一条主动离开运行的边** |
| ⑤ | 阻塞 → 就绪 | 事件发生（I/O 完成、被 V 唤醒、中断处理完毕） | **被动**（由中断/其他进程/硬件"叫醒"） | 注意：**阻塞→就绪 ≠ 阻塞→运行**！醒来后还要排队等调度 |
| ⑥ | 运行 → 终止 | 正常结束（main 返回）/异常退出（越界、非法指令） | 正常结束为**主动**；异常为**被动强制**（OS 强制终止） | 广义上"退出操作"可以由 OS 强制 |

> 【核心结论】① 只有**就绪→运行**能"进入"运行态；② 只有**运行→就绪/阻塞/终止**能"离开"运行态；③ **不存在"阻塞→运行"**（必须醒来后先回就绪排队）；④ **不存在"就绪→阻塞"**（没跑 CPU 怎么会去等待 I/O？）。

## 2.2.3 【易错】常见错误转换辨析

很多同学把状态转换图背串了，考场上对"下面哪个转换可能存在"犹豫不决。图 2-4 把所有"你可能会以为可以、但实际不存在"的箭头一次讲清：

![2-4 状态转换易错辨析](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-05_forbidden_transitions.png)

*图2-4 状态转换易错图：四种"你以为可以"的捷径都不存在，右边红框解释"为什么"。*

| 错误转换 | 为什么不存在（答题话术） |
| --- | --- |
| ~~阻塞 → 运行~~ | 阻塞进程的"事件"还没发生，即使 CPU 空着也不能运行；事件发生（被唤醒）后只能先进入**就绪**状态，再**被调度**才能运行 |
| ~~就绪 → 阻塞~~ | 就绪进程没拿到 CPU，根本没有在执行，不可能"主动请求 I/O"——只有**运行态**进程才能等待事件转入阻塞 |
| ~~创建 → 运行~~ | 创建完成后先放入就绪队列排队等待调度，不能"一步到位"直接上 CPU |
| ~~终止 → 就绪/阻塞~~ | 进程终止即"死亡"，PCB 被回收，实体不复存在；"复活"必须重新调用创建原语 |

> 【最大考点辨析】**"运行→阻塞"是主动；"阻塞→就绪"是被动；"就绪→运行"是被动；"运行→就绪"（时间片完/被抢占）是被动。** 一句话：**除了"运行→阻塞"这一条主动边，其他边基本都是 OS/硬件主导的"被动边"。** 唯一例外："运行→终止"如果是程序正常结束返回，那是进程自己的行为（主动结束）。

#### 深化学习：就绪队列与阻塞队列——"排队的人"长什么样

五状态图是"抽象人"，落到系统里，排队的结构长这样：

![2-29 就绪队列与阻塞队列全景](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-29_ready_block_queues.png)

*图2-29 就绪队列与阻塞队列全景：就绪队列排的是"CPU"这一种资源；阻塞队列按"等的事件"分组（等磁盘/等键盘/等打印），两组人互不相干。*

**图后解读要点**：

- **为什么"阻塞→运行"不存在，看队列就懂**：阻塞队列里的进程排的是"磁盘/键盘/打印机"的队，跟 CPU 的队完全是两家——就算 CPU 现在闲着，也不会"叫到"阻塞队列里的人；必须先由**中断唤醒**转回**就绪队列**重新排队；
- **阻塞队列不止一个**：按等待**事件**分组（等 I/O 的、等消息的、等信号的），事件发生时只唤醒**对应队列**里的进程——这也是唤醒原语要"指明事件"的原因；
- 【延伸·选择题点】"就绪队列一定只有一个" → **错**。采用**多级队列/多级反馈队列**调度（见 2.6）时，就绪队列按优先级分层，有多个。

## 2.2.4 七状态模型：挂起（Suspend）

当内存紧张或进程暂时用不到时，OS 可以把进程**整体换出到外存**（挂起），以后需要再换回（激活）。这就是**中级调度**（也叫**内存调度**）的职责。加上挂起后的"静止"状态,五状态就扩展成了**七状态**：

![2-5 七状态模型](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-04_seven_states.png)

*图2-5 七状态模型：活动就绪↔静止就绪、活动阻塞↔静止阻塞 两对"挂起/激活"边；挂起由中级调度实施。*

要点：

1. **挂起（Suspend）**：把进程**换出内存**（放到外存），进程暂时**不参与 CPU 调度**。**激活（Activate）**：把挂起的进程**换回内存**，重新参与调度。
2. 两对边：
   - **就绪 ↔ 静态就绪（就绪挂起）**：活动就绪被挂起→静止就绪；静止就绪被激活→活动就绪。
   - **活动阻塞↔静止阻塞**：阻塞进程也可被挂起（节省内存）；激活后仍是阻塞（外存里等事件），事件发生后再变成静止就绪，再激活才回活动就绪。
3. **挂起前后状态变了没有？** ——静止就绪/静止阻塞都是"挂起"的状态；**"被挂起的进程不参与调度"**。
4. 引入挂起的原因（选择题）：① 内存不够、负载太重（先把不活跃的换出）；② 父进程请求 / 调试需求（暂时冻结）；③ 系统负载均衡；④ 故障恢复（检查点）。

> 【考点】"被挂起的进程处于什么状态？—— 静止就绪（就绪挂起）/ 静止阻塞（阻塞挂起），两者都不在内存中、都不参与调度。**中级调度（内存调度）就是管理"挂起与激活"的调度。** 它与低级调度（进程调度）的区别：中级调度的对象是**进/出外存**，低级调度的对象是**上/下 CPU**。

## 2.2.5 【考点】给事件序列，写状态变化（真题必练）

**【真题风格例题 1】** 一进程依次发生如下事件：① 创建完成；② 被调度选中；③ 用满一个时间片；④ 请求读磁盘；⑤ 磁盘传输完成（其中断处理）；⑥ 再次被调度选中；⑦ 程序执行完毕。写出各事件后的状态。

**解**：

| 事件 | 状态变化 | 依据 |
| --- | --- | --- |
| ① 创建完成 | 创建态 → **就绪** | 创建完成后插入就绪队列 |
| ② 被调度选中 | 就绪 → **运行** | 获得 CPU |
| ③ 时间片用完 | 运行 → **就绪** | 被剥夺，回到队尾 |
| ④ 请求读磁盘 | 运行 → **阻塞** | **主动**等待 I/O |
| ⑤ 磁盘传送完成 | 阻塞 → **就绪** | 中断唤醒（被动） |
| ⑥ 再次被调度 | 就绪 → **运行** | 获得 CPU |
| ⑦ 执行完毕 | 运行 → **终止** | 正常结束 |

> 【易错点】事件 ⑤ 之后进程仍在**就绪**状态——很多同学写成"阻塞→运行"，错！它必须排在就绪队列里等待被调度（事件 ⑥）。

#### 专项训练：一张时间线图吃透"事件→状态"

![2-28 状态转换序列例题时间线](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-28_state_sequence_example.png)

*图2-28 进程 P 的一生：创建→就绪→运行→（请求打印）阻塞→（打印完成）就绪→运行→终止，每个箭头上标注触发事件与主动/被动。*

**做题模板（三句话）**：

1. 每发生一个事件，只检查"**谁变、变成什么**"——一次只动一条边，不要凭想象连跳两步；
2. **"主动请求 I/O / 等信号量" = 运行→阻塞**；**"时间片到 / 被抢占" = 运行→就绪**——先分清主动被动，再动笔；
3. **"事件完成"类中断（I/O 完成）带来的永远是"阻塞→就绪"**，绝不直接进运行态。

**【真题风格例题 2 · 双进程交替】** 两进程 P、Q 共享一台打印机：P 运行中发出打印请求；此时 Q 被调度运行；打印完成后 P、Q 竞争 CPU。写出 P 的状态变化序列。
**解**：P：运行 →（请求打印，主动）**阻塞** →（打印完成中断，被动）**就绪** →（被调度，被动）**运行**。注意中间任何一步都不出现"阻塞→运行"。

# 2.3 进程控制

## 2.3.1 原语：不可中断的"最小的"操作

进程的**创建、撤销、阻塞、唤醒**都涉及对 PCB 和状态队列的修改，**一旦中途被打断就会出错**（比如 PCB 刚建了一半，状态和队列对不上）。因此 OS 用**原语（Primitive）**来实现这些操作：

- **原语 = 原子操作**：要么全部做完，要么一个都不做，**中间不可被中断**。
- 实现手段：**关中断**（CPU 在处理原语期间不响应中断，保证原子性），执行完再**开中断**。单 CPU 下关中断就能保证原子性；多核环境下还要配合锁等其他机制。
- 进程控制原语 **一定运行在核心态**（需要访问内核数据结构、修改 PCB）。

> 【易错】"关中断"≈"原子性"（单处理机下）；但**关中断只针对单处理器**. 另外"关中断时限"要短，否则系统对其他中断（如时钟、I/O）响应不及时。

## 2.3.2 五种进程控制原语（做什么、何时触发、状态怎么变）

![2-6 五种进程控制原语](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-06_process_primitives.png)

*图2-6 五种原语：创建、撤销、阻塞、唤醒、切换——各自对应一组状态转换。*

| 原语 | 做什么 | 触发时机 | 状态转换 |
| --- | --- | --- | --- |
| **创建**（Create） | ① 申请空白 PCB ② 分配内存等资源 ③ 初始化 PCB（装入程序）④ 插入就绪队列 | 终端登录 / 作业调度 / 提供服务（如打印）/ 应用请求 | 创建态 → **就绪** |
| **撤销**（Terminate） | ① 从 PCB 表删除 ② **递归撤销其全部子孙进程** ③ 归还资源、回收 PCB | 正常结束 / 异常退出 / 外界干预（强制 kill） | 运行/就绪/阻塞 → **终止** |
| **阻塞**（Block） | ① 保存现场 ② 改为阻塞态、移出就绪队列 ③ 转入阻塞队列等事件 | **运行态**进程请求 I/O 或等待事件 | 运行 → **阻塞**（主动） |
| **唤醒**（Wakeup） | ① 从阻塞队列取出 ② 改为就绪态 ③ 插入就绪队列 | 事件发生（I/O 完成、被 V 唤醒）——由中断、其他进程或硬件引起 | 阻塞 → **就绪**（被动） |
| **切换**（Dispatch） | ① 保存原进程运行现场（写入其 PCB）② 更新其 PCB 状态 ③ 选新进程、恢复其现场 | 时间片用完 / 更高优先级到达 / 运行进程结束或阻塞 | 就绪 ↔ **运行** |

> 【易错·高频】① **阻塞与唤醒必须成对**：阻塞多少进程，就必须对应地被唤醒多少次（每个被阻塞的进程最终都得由某个 V/事件唤醒）。② **进程切换一定发生在核心态**（上下文切换要访问 PCB 等内核结构）。③ 撤销父进程必须**递归**撤销子孙（树形结构），否则留下"孤儿"垃圾进程。④ 创建后进入**就绪**，**不是运行**。

# 2.4 进程通信（IPC）

进程拥有**独立的地址空间**——A 进程不能直接改 B 进程的内存（这是设计上的安全），所以要通信，必须通过操作系统提供的机制：

![2-7 进程通信的三种方式](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-07_ipc_overview.png)

*图2-7 三种通信方式：共享存储、消息传递（信箱）、管道。*

## 2.4.1 共享存储（Shared Memory）

在内存中开辟一块**共享区域**，两个进程各自把它映射到自己的地址空间，然后直接读写这块区域（通信最快、最灵活）。

| 分类 | 说明 | 特点 |
| --- | --- | --- |
| **基于数据结构的共享** | 共享一个数据结构（如共享数组、共享队列） | 效率低、**低级**；通信量小，且用户要自己处理同步问题 |
| **基于存储区的共享** | 专门划出一块共享内存区 | 通信速度快、**高级**；仍是用户负责同步互斥 |

> 【考点】共享存储最大的特点是"**通信双方直接在共享区读写，不再由 OS 传递数据**"——因此速度最快；代价是**同步互斥要自己保证**（超纲点：现代 OS 常用"信号量 + 共享内存"组合）。

## 2.4.2 消息传递（Message Passing）

以"消息"为单位，由 **OS 负责安全传递**（消息 = 消息头 + 正文）。分两种：

- **直接通信**：发送方**指名道姓**（send(接收进程名, 消息)），消息直接挂到接收进程的队列。
- **间接通信**：发送方不指定接收者，而是把消息放入**信箱（Mailbox）**，接收方从信箱里取——中间实体是信箱。

> 【考点】"消息传递由操作系统保护，安全性好但速度慢"；直接通信是"点对点"，间接通信是"通过中间人"。**共享存储是"用户自己搬东西"，消息传递是"OS 代劳送货"**——速度 vs 安全的取舍。

#### 深化学习：直接 vs 间接通信一图看清

![2-30 直接通信与间接通信](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-30_ipc_direct_indirect.png)

*图2-30 直接通信：send(P2, msg) 点对点直送；间接通信：消息经共享信箱 M 中转，收发双方只认信箱不认人。*

**图后解读要点**：

- **直接通信的"耦合"问题**：P1 的代码里写死了 `send(P2, msg)`——P2 改名，P1 就得改；一对一固定，灵活性差；
- **间接通信的"解耦"红利**：双方只认信箱 M。同一个信箱可以被**多个**进程收发 → 天然支持**多对多**广播；信箱归 OS 管理，还可做**收件箱容量限制**（信箱满则发送者阻塞——又是一个生产者-消费者模型！）；
- 【考点】判断题"间接通信方式中，接收进程必须显式指明消息的发送者" → **错**（它只指明**信箱**）；
- 【延伸】无论直接/间接，消息传递都要**内核提供 send/receive 原语**、数据要经内核"拷贝两次"（发送方→内核缓冲→接收方），这就是它比共享存储慢的根源。

## 2.4.3 管道（Pipe）——"一根水管"

管道本质上是**内存中的一个固定大小的缓冲区**，由一个"写端"和一个"读端"连接两个进程，数据像水一样从写端流向读端：

![2-8 管道通信](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-08_pipe.png)

*图2-8 管道：写进管道的数据先进先出（FIFO）、读走即删；写满阻塞写者、读空阻塞读者；访问需互斥。*

**管道四大特性（逢考必出）**：

| 特性 | 含义 |
| --- | --- |
| ① **半双工** | 数据**只能单向流动**；若要双向通信必须建立**两根管道**（A→B 一根，B→A 一根） |
| ② **写满阻塞写者** | 管道缓冲区满时，写进程的 write 操作被阻塞，等读者取走数据 |
| ③ **读空阻塞读者** | 管道缓冲区空时，读进程的 read 操作被阻塞，等写者写入数据 |
| ④ **互斥访问** | 管道是临界资源，读写双方对管道的访问必须互斥——由 OS 保证 |

**本质**：管道通信 = **"生产者-消费者"模型**（写端=生产者，读端=消费者）。

> 【真题风格例题 2】关于管道通信，下列说法正确的是（ ）。
> A. 管道既可用于进程间通信，也可用于网络通信
> B. 管道是操作系统在内存中开辟的缓冲区，数据读取后立即删除
> C. 管道支持全双工通信
> D. 管道访问不需要同步机制
>
> **答案 B**。解析：A 错——管道是**单机进程间**通信，网络通信走消息；B 对——读走即删、不能回读；C 错——**半双工**，要双向得两根管道；D 错——必须互斥（特性④）。

**【记忆口诀】"半双工、FIFO、写满堵写、读空堵读、互斥用 OS 保"。**

# 2.5 线程（Thread）

## 2.5.1 为什么引入线程？

想想 2.4 的问题：进程切换要**换地址空间（"搬房子"）**、换目录缓存（TLB 失效）——开销大。可是很多情景下，我们希望同一进程里的几件事**并发执行**（比如浏览器：一个线程下载图片、一个线程渲染页面、一个线程监听鼠标），它们共享进程的代码和数据，**共用一间"房子"**，切换时**只换"现场"（PC、寄存器、栈）**就好了。

于是引入 **线程**：

- **线程 = 轻量级进程（LWP）**，是 **CPU 调度的基本单位**。
- **进程** 则退居为 **资源分配的基本单位**（拥有地址空间、打开的文件等）。

> 【考点一句话】**进程：资源分配的基本单位；线程：处理机调度的基本单位。** 一个进程可以有多个线程，线程共享进程的资源。

## 2.5.2 线程的属性：独有什么、共享什么

线程是一个"执行流"，它**不能独立拥有资源**——只拥有保证自己运行的最小"现场"：

![2-9 线程的资源视图](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-09_thread_sharing.png)

*图2-9 同进程的线程共享：地址空间、全局变量、打开的文件、堆、设备与信号量等资源；每个线程独有：线程ID、程序计数器PC、寄存器组、栈。*

| 线程独有（"现场"） | 同进程线程共享（"房屋"） |
| --- | --- |
| 线程 ID（TID） | 地址空间（**代码段、数据段、堆**） |
| 程序计数器 PC | 全局变量（可以直接互相访问） |
| 寄存器组 | 已打开的文件（文件描述符表） |
| **栈**（函数调用现场、局部变量） | 打开的设备、信号量等资源 |

> 【易错】**堆（Heap）是共享的，栈（Stack）是独有的！** 不要记反。共享堆 + 独立栈意味着：线程间可以直接用全局变量/堆对象通信（不需要 IPC），但由于共享，**必须要自己同步互斥**（这正是 2.7 的内容）。

**线程属性总结**：① **轻量级**（切换开销小）；② **独立调度**（可被单独调度）；③ **共享资源**；④ 并发性；⑤ 无独立的资源分配（资源属于进程）。

### 进程 vs 线程 大对比表（必背）

| 比较项 | 进程 | 线程 |
| --- | --- | --- |
| 基本单位角色 | **资源分配**的基本单位 | **处理机调度**的基本单位 |
| 地址空间 | 各进程独立（不能直接互访） | 同进程线程共享（可直接互访） |
| 拥有资源 | 完整资源（代码、数据、文件、设备…） | 只有运行现场（TID、PC、寄存器组、栈） |
| 切换开销 | 大：换地址空间、刷新 TLB；要进核心态完成切换 | 小：同一进程内只换"现场"（用户级线程连核心态都不用进） |
| 通信 | 需要 IPC（共享存储/消息/管道） | 共享全局变量即可（仍要同步） |
| 并发粒度 | 大 | 小 |
| 系统开销 | 创建/撤销开销大 | 创建/撤销开销小 |
| 出错影响 | 一个进程崩溃与其他进程隔离 | 一个线程崩溃往往拖垮整个进程 |

## 2.5.3 用户级线程（ULT）与内核级线程（KLT），多线程模型

| 类别 | 实现 | 内核是否看得见 | 切换是否进核心态 | 优缺点 |
| --- | --- | --- | --- | --- |
| **用户级线程 ULT** | 由用户空间的**线程库**管理（Create/Switch 都是库函数） | 内核**看不见**，内核只看到一个进程 | **不需要**进核心态（纯用户态切换，开销最小） | 优点：切换快、无需内核支持；**缺点：一个 ULT 阻塞 → 整个进程阻塞（内核以为进程挂了）；无法利用多核并行** |
| **内核级线程 KLT** | 线程在内核中创建、管理、调度 | 内核看得见、可为每个 KLT 分配 CPU | **需要**进核心态，每次切换开销比分进程小、比 ULT 大 | 优点：真正并行、一个阻塞不影响其他；缺点：切换进核心态、开销较大 |
| **多线程模型**：多对一 / 一对一 / 多对多 | 见下图 | — | — | Windows/Linux 采用 KLT（一对一）；Java 早期是"一对一"（JVM + 内核），后来也有用户级库（如 Go 的 goroutine） |

![2-10 线程映射模型](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-10_thread_mapping.png)

*图2-10 三种映射模型：多对一（多个用户线程映射到一个内核线程）、一对一、多对多（m 个用户线程映射到 n 个内核线程，m＞n）。*

| 模型 | 含义 | 特点 | 代表 |
| --- | --- | --- | --- |
| **多对一** | 多个 ULT 映射到 1 个 KLT | 切换快；**一个 ULT 阻塞 → 整个进程阻塞**；不能利用多核 | 早期线程系统（如部分旧 UNIX 库） |
| **一对一** | 一个 ULT 对应一个 KLT | 真正并行、一个阻塞不碍事；**切换要进核心态，开销较大** | Windows、Linux（现代主流） |
| **多对多（m:n）** | m 个 ULT 映射到 n 个 KLT（m＞n） | 兼有两者优点：既不多、也不少——并行度可控，阻塞不牵连 | 一些新式库/内核 |

> 【考点·常考辨析】"线程切换是否需要进入核心态？" —— **用户级线程：不需要**（线程库在用户态完成切换，内核无感知）；**内核级线程：需要**（线程表在内核中）。所以"线程切换一定比进程切换快"并不绝对：**用户级线程切换确实最快**；内核级线程切换也比分进程快（不用换地址空间），但比 ULT 慢。
>
> 【易错】"一个线程被阻塞后，同进程的其他线程还能运行吗？"——**内核级线程：能**；**用户级线程：不能**（内核把进程整体阻塞了）。这是“多对一模型”的致命缺陷——“一个 ULT 阻塞 → 整个进程阻塞”。

#### 深化学习：线程切换到底发生在哪一层

![2-31 用户级线程与内核级线程的切换路径](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-31_ult_klt_switch.png)

*图2-31 ULT：T1→T2 切换由用户态线程库完成，不进内核（快，但 T1 阻塞会连坐整个进程）；KLT：切换要陷入内核，由内核调度（慢一点，但可真并行）。*

**图后解读要点（把"切换开销"这条线算清楚）**：

- **ULT 切换 = 换一组寄存器 + 换栈指针**，纯用户态函数调用级别的开销（纳秒级），内核全程无感；
- **KLT 切换 = 陷入内核（态切换）+ 内核调度决策 + 恢复**，开销介于 ULT 和进程切换之间；
- **进程切换 = KLT 切换 + 换地址空间（页表基址寄存器）+ TLB/缓存失效**，最贵；
- **性能排序（选择题常考）**：ULT 切换 < KLT 切换 < 进程切换；
- **代价排序反过来**：ULT 的"一阻全阻 + 用不了多核"最伤——所以现代主流系统（Linux/Windows）都用**一对一（KLT）**模型，把并发性放在第一位。

# 2.6 处理机调度

## 2.6.1 三级调度：高级、中级、低级

![2-11 三级调度](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-11_scheduling_levels.png)

*图2-11 三级调度：高级调度（作业调度，外存→内存）、中级调度（内存调度，挂起/激活）、低级调度（进程调度，就绪→CPU）。*

| 调度 | 别名 | 对象 | 干什么 | 频率 |
| --- | --- | --- | --- | --- |
| **高级调度** | 作业调度 | **外存**后备队列→**内存** | 选中作业、创建进程、分配资源（对应"创建→就绪"） | 最低（几分钟一次） |
| **中级调度** | **内存调度** | 内存 ↔ 外存 | **挂起/激活**（对应 2.2.4 七状态） | 可高可低 |
| **低级调度** | 进程调度 | 就绪队列 → CPU | **真正分配 CPU**（对应"就绪→运行"） | 最高（毫秒级） |

> 【考点】**只有低级调度真正把 CPU 分给进程**；高级/中级调度只管进程"进场/出场（进内存/出外存）"。三级调度的关系与 2.2 的七状态模型是**一一对应**的：高级调度产生"创建→就绪"，中级调度产生"挂起/激活"，低级调度产生"就绪→运行"。

## 2.6.2 调度时机：什么时候"可以"调度？

**需要调度的时机**（发生以下事件后，系统会检查是否需要重新调度）：

1. 运行进程**正常终止**或异常退出；
2. 运行的进程**主动阻塞**（请求 I/O、等待事件）；
3. 时间片用完（RR）或被**更高优先级**进程抢占（抢占式）；
4. 中断返回（I/O 完成，有更急迫的进程就绪）。

**不能调度的三种情形**（高频辨析题）：

| 情形 | 说明 |
| --- | --- |
| ① **处理中断的过程中** | 中断处理必须在关中断态一口气做完（否则会丢中断、乱现场） |
| ② **进程处于 OS 内核的临界区内** | 内核临界区（如修改资源分配表、操作系统本身的共享数据结构）不能被剥夺，否则其他进程也进不了该临界区（拒绝剥夺式调度） |
| ③ **原子操作过程中** | 原语（P/V 等）执行中不可中断 |

> 【易错·重点辨析】**"进程处于临界区时不能进行调度"这句话是错误的！** 只有"**OS 内核的临界区**"才不能抢占。**普通进程的临界区**（如用户访问自己的共享变量）**可以进行调度**——因为抢占它顶多让它多等一会儿，不会破坏系统数据。

## 2.6.3 调度方式：抢占式 vs 非抢占式

- **非抢占式（非剥夺式）**：进程一旦获得 CPU 就**一直运行到结束或阻塞**，中途不被抢走。
- **抢占式（剥夺式）**：允许 OS（按优先级、时间片等策略）**从运行进程手中夺回 CPU**。响应快、适合交互式系统。

**闲逛进程（Idle）**：当所有进程都阻塞、系统空闲时，CPU 不能"停摆"——调度器会调度一个**闲逛进程**（优先级最低）。它不执行任何用户代码，可被随时抢占；作用只是"把空闲 CPU 消耗掉、保持系统运行"。

> 【考点】"只要系统中有可运行的进程，CPU 就不会空闲"；闲逛进程不可被用户捕获，且通常**优先级最低**，总是等所有其他进程都就绪/阻塞时才轮得到。

## 2.6.4 评价指标：先会算，再谈好坏

| 指标 | 定义 | 说明 |
| --- | --- | --- |
| **CPU 利用率** | CPU 有效工作时间 / 总时间 | 越高越好 |
| **系统吞吐量** | 单位时间内完成作业数 | 越高越好 |
| **周转时间** | **完成时间 − 到达时间** | 越小越好；含等待+运行+排队 |
| **带权周转时间** | **周转时间 / 服务时间（运行时间）** | ≥1；越小越好，**更能体现"相对公平"** |
| **等待时间** | 进程在**就绪队列排队**的时间合计（＝周转 − 运行时间） | 越小越好 |
| **响应时间** | 从**提交**到**首次获得 CPU** 的时间 | 交互系统最关注 |

> 【考点】**带权周转 ＝ 周转 / 服务**（服务就是"它需要在 CPU 上跑的时间"）。做题时三件套：先画**甘特图**（谁在什么时候占 CPU），再逐个写**完成时间**，最后求**周转、带权周转、平均值**。

【记忆口诀】**"周转=完成-到达；带权=周转/服务；等待=周转-运行。"**

## 2.6.5 六大调度算法（逐个来）

先看一图总览（六个小示意 + 一句话特征）：

![2-12 六种调度算法一览](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-14_scheduling_compare.png)

*图2-12 六种算法一览：FCFS 谁先到、SJF 谁短、HRRN 谁比值高、RR 轮流、优先级 谁重要、MLFQ 层层降。*

### (1) FCFS 先来先服务

- **规则**：按**到达时间**先后排队，**非抢占**。
- **优点**：最简单、公平（排队买票）；长作业不饥饿。
- **缺点**：**对短作业不利**——短作业前面排一个大长作业，等得久。
- **适用**：对优先级无要求、作业长短差别不大的场合。

### (2) SJF 短作业优先（最短作业优先，SPF）

- **规则**：**服务时间最短**的先运行（**非抢占**；抢占版叫 **SRTN 最短剩余时间优先**）。
- **优点**：**平均等待时间、平均周转时间最小**（数学上可证明"最优"）。
- **缺点**：① 需要**预知**运行时间（实际做不到，只能估算）；② **长作业容易饥饿**（"饥饿"：永远轮不到）。
- **适用**：批处理系统；不适用于交互。

### (3) HRRN 高响应比优先

- **规则**：每次调度时，选**响应比最大**的进程：

> **响应比 ＝ (等待时间 + 要求服务时间) / 要求服务时间 ＝ 1 ＋ 等待时间/服务时间**

- 特点：**SJF 越短比值越高**（短作业优先），**等待越久比值越高**（有"待得久者优先"的补偿），优点 = FCFS 的公平 + SJF 的高效。
- **缺点**：每次调度都要比较计算，**开销稍大**；且依旧是**非抢占**。
- **公式记忆**：响应比 = 1 + 等待/服务（等待越长、服务越短都加分）。

### (4) RR 时间片轮转

- **规则**：就绪队列按到达序排好，每个进程**运行一个时间片 q** 后被剥夺、排到队尾（**抢占式**）。
- **时间片的影响**：
  - q **太大** → 几乎退化为 FCFS（每个进程都跑很久才让位），响应变差；
  - q **太小** → 每个进程都频繁切换，**进程切换开销**占了很大比例，CPU 有效利用率下降（切换也是要花时间的）。
- **优点**：响应时间短，**交互式友好**、公平；**缺点**：切换开销、平均周转不一定最优。

### (5) 优先级调度

- **规则**：优先级**高者先运行**。分**静态优先级**（创建时定死）与**动态优先级**（运行中变化，如"等待越久优先级越高"）。
- **抢占式**：高优先级进程一到，立即打断正在运行的低优先级进程。
- **缺点**：**低优先级进程可能永远等不到 CPU（饥饿）**；解决方法：**"老化"**——让等待越久的进程优先级逐渐提高。
- 【易错】**静态优先级易饥饿，动态优先级（老化机制）可缓解饥饿**。

### (6) 多级反馈队列（MLFQ）——"本尊"

![2-13 多级反馈队列](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-15_mlfq.png)

*图2-13 MLFQ：多个就绪队列，优先级从高到低、时间片从短到长。新进程进 Q1；用完一个时间片未完成→降级到下一队列；高优先级队列非空时抢占低优先级。*

- **规则**：① 设置多个就绪队列，Q1 优先级最高、时间片最小（如 1）；Q2 次之（如 2）；Q3 最低、时间片最大（如 4）。② **新进程先进入 Q1**。③ 在 Q1 用完时间片仍未完成 → **降级到 Q2**；Q2 用完仍未完成 → Q3…… ④ **只有在高优先级队列为空时，才调度低优先级队列**；高优先级有新进程到达，立即抢占低优先级运行的进程。⑤ 每个队列内部一般用 **FCFS**（也有用 RR）。
- **优点**：**短作业在 Q1 快速完成**（响应快）；**长作业逐级下放、时间片越来越大**（等待越久时间片越大，不会饿死）；无需预知运行时间；兼顾**响应时间与吞吐量**。
- **缺点**：实现较复杂；长任务被"逐级下放"，若各级都用 FCFS 仍可能有延迟。

**多级反馈队列 = "多队列 + 优先级递减 + 时间片倍增"**，是优先级和 RR 的组合，也是现代交互系统（如 Linux 早期调度器）的设计思想雏形。

### 六大算法对比总表

| 算法 | 抢占 | 饥饿 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- | --- |
| FCFS | 否 | 无 | 简单、公平 | 短作业吃亏 | 批处理（作业长短均匀） |
| SJF | 否（SRTN 是） | **长作业饥饿** | 平均等待/周转最小 | 需预知时间、长作业饿 | 批处理 |
| HRRN | 否 | 缓解（比值补偿） | 兼顾公平与高效 | 每次要算比值 | 批处理 |
| RR | 是 | 无 | 响应快、交互友好 | 切换开销、q 难定 | **分时/交互** |
| 优先级 | 可 | **低优先级饥饿** | 灵活、重要者优先 | 饥饿（用"老化"缓解） | 实时/分级系统 |
| MLFQ | 是 | 基本无 | 响应+吞吐兼顾 | 实现复杂 | 通用/交互 |

> 【记忆口诀】**"F 先到、S 最短、H 比长短、R 轮流、P 看重要、M 层层降"**——前五种都是"单队列型"，多级反馈队列是"多队列型"。

## 2.6.6 【必做综合例题】同一组数据，四种算法全算一遍

**题目**：四进程到达时间与服务时间如下（单位：时间片，时间从 0 开始）：

| 进程 | 到达时间 | 服务时间 |
| --- | --- | --- |
| P1 | 0 | 7 |
| P2 | 2 | 4 |
| P3 | 4 | 1 |
| P4 | 5 | 4 |

> **解题总流程（三步走）**：① 画甘特图（谁在 [a,b] 时间段占 CPU）；② 由甘特图读完成时间；③ 求周转＝完成−到达、带权＝周转/服务、平均。

### (1) FCFS 先来先服务

![2-14 FCFS 与 SJF 甘特图](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-12_gantt_fcfs_sjf.png)

*图2-14 同一组数据下 FCFS（上）与 SJF（下）的甘特图对比：FCFS 的 P2 要等 P1 跑完（到 t=7 才开始），SJF 则把最短的 P3 提到前面，P2 反而多等了。*

**甘特图**：P1[0,7] → P2[7,11] → P3[11,12] → P4[12,16]。

| 进程 | 完成 | 周转 | 带权周转 | 等待 |
| --- | --- | --- | --- | --- |
| P1 | 7 | 7 − 0 = **7** | 7/7 = **1.00** | 0 |
| P2 | 11 | 11 − 2 = **9** | 9/4 = **2.25** | 5 |
| P3 | 12 | 12 − 4 = **8** | 8/1 = **8.00** | 7 |
| P4 | 16 | 16 − 5 = **11** | 11/4 = **2.75** | 7 |
| **平均** | — | **(7+9+8+11)/4 = 8.75** | **(1+2.25+8+2.75)/4 = 3.50** | 4.75 |

### (2) SJF 最短作业优先（非抢占）

**逐步演算**：t=0 只有 P1（P2 还没到）→ P1 先跑。[0,7] 结束，此时就绪队列：P2(服务4,达2)、P3(服务1,达4)、P4(服务4,达5)。**谁短谁先**：P3(1) < P2(4)=P4(4)。→ P3[7,8]。t=8 时 P2 与 P4 服务时间**相等**——按"到达时间早者优先"（先到先服务作平局裁决）选 P2 → P2[8,12] → P4[12,16]。

**甘特图**：P1[0,7] → P3[7,8] → P2[8,12] → P4[12,16]。

| 进程 | 完成 | 周转 | 带权周转 | 等待 |
| --- | --- | --- | --- | --- |
| P1 | 7 | 7 | 1.00 | 0 |
| P3 | 8 | 8−4 = **4** | 4/1 = **4.00** | 3 |
| P2 | 12 | 12−2 = **10** | 10/4 = **2.50** | 6 |
| P4 | 16 | 16−5 = **11** | 11/4 = **2.75** | 7 |
| **平均** | — | **8.00** | **2.5625** | 4.00 |

> 对比：SJF 的平均周转（8.00）明显优于 FCFS（8.75）——**短作业插队，大家都少等**。代价是 P2 比 FCFS 多等了 1 个时间单位（8 才跑 vs 7 就跑）。

### (3) HRRN 高响应比优先（非抢占）

![2-15 HRRN 与 RR 甘特图](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-13_gantt_hrrn_rr.png)

*图2-15 同一组数据下 HRRN（上）与 RR(q=1)（下）的甘特图。RR 加注了"同一时刻：新到达进程先入队、被抢占进程后入队"的约定与每片 1 单位的时间刻度。*

**逐步演算（每次调度算一次响应比，响应比 = 1 + 等待/服务）**：

- t=0：只有 P1 → P1[0,7]。
- t=7：就绪 P2、P3、P4。
  - P2：等待 7−2=5 → 响应比 (5+4)/4 = **2.25**
  - P3：等待 7−4=3 → (3+1)/1 = **4.00** ← 最大
  - P4：等待 7−5=2 → (2+4)/4 = **1.50**
  - → 选 **P3**，P3[7,8]。
- t=8：就绪 P2、P4。
  - P2：等待 8−2=6 → (6+4)/4 = **2.50** ← 最大
  - P4：等待 8−5=3 → (3+4)/4 = **1.75**
  - → 选 **P2**，P2[8,12] → P4[12,16]。

**甘特图**：P1[0,7] → P3[7,8] → P2[8,12] → P4[12,16]（与 SJF 完全一致——本例中短作业 P3 的响应比一开始就最高）。

| 进程 | 完成 | 周转 | 带权周转 |
| --- | --- | --- | --- |
| P1 | 7 | 7 | 1.00 |
| P3 | 8 | 4 | 4.00 |
| P2 | 12 | 10 | 2.50 |
| P4 | 16 | 11 | 2.75 |
| **平均** | — | **8.00** | **2.5625** |

### (4) RR 时间片轮转（q = 1）

**约定（必须写进答题）**：**同一时刻新到达的进程先入队、时间片用完被抢占的进程后入队**（两者都排在队尾；新到达者排在"被抢占者"之前，已经在队列里等待的进程仍然排在前头），每片 1 个时间单位。

**逐步推演（请对照甘特图逐行看）**：

| 时间片 | 运行进程 | 该时刻末的就绪队列（队首←队尾） | 说明 |
| --- | --- | --- | --- |
| [0,1] | P1 | P1 | P2 未到，P1 连续运行 |
| [1,2] | P1 | P1 | P1 已用 2/7 |
| t=2 | — | **P2, P1** | P2 到达（先入队），P1 时间片用完（后入队） |
| [2,3] | P2 | P1 | P2 用 1/4 |
| t=3 | — | **P1, P2** | P2 时间片用完，排到队尾 |
| [3,4] | P1 | P2 | P1 用 3/7 |
| t=4 | — | **P2, P3, P1** | P3 到达（14 时刻，排在已等待的 P2 之后、被抢的 P1 之前） |
| [4,5] | P2 | P3, P1 | P2 继续用（2/4） |
| t=5 | — | **P3, P1, P4, P2** | P4 到达先入队；P2 被抢占后入队 |
| [5,6] | P3 | P1, P4, P2 | P3 用满 1 片即完成：**P3 完成时间 = 6** |
| [6,7] | P1 | P4, P2 | P1 用 4/7 |
| [7,8] | P4 | P2, P1 | P4 用 1/4 |
| [8,9] | P2 | P1, P4 | P2 用 3/4 |
| [9,10] | P1 | P4, P2 | P1 用 5/7 |
| [10,11] | P4 | P2, P1 | P4 用 2/4 |
| [11,12] | P2 | P1, P4 | P2 用满 4 片：**P2 完成时间 = 12** |
| [12,13] | P1 | P4 | P1 用 6/7 |
| [13,14] | P4 | P1 | P4 用 3/4 |
| [14,15] | P1 | P4 | P1 用满 7 片：**P1 完成时间 = 15** |
| [15,16] | P4 | （空） | P4 用满 4 片：**P4 完成时间 = 16** |

> **复核**：P1 获得 7 片（0-1、1-2、3-4、6-7、9-10、12-13、14-15）；P2 获得 4 片（2-3、4-5、8-9、11-12）；P3 获得 1 片（5-6）；P4 获得 4 片（7-8、10-11、13-14、15-16）。总片数 = 16，与总服务时间 16 吻合，且 CPU 从 t=0 到 t=16 连续运行、无空闲。

**结果**：

| 进程 | 完成 | 周转 | 带权周转 | 获得时间片 |
| --- | --- | --- | --- | --- |
| P3 | **6** | 6−4 = **2** | 2/1 = 2.00 | 5-6 |
| P2 | **12** | 12−2 = **10** | 10/4 = 2.50 | 2-3, 4-5, 8-9, 11-12 |
| P1 | **15** | 15−0 = **15** | 15/7 ≈ 2.14 | 0-1, 1-2, 3-4, 6-7, 9-10, 12-13, 14-15 |
| P4 | **16** | 16−5 = **11** | 11/4 = 2.75 | 7-8, 10-11, 13-14, 15-16 |
| **平均** | — | **(2+10+15+11)/4 = 9.50** | **(2+2.5+2.14+2.75)/4 ≈ 2.35** | — |

> 【重要说明·与参考值的差异】常见参考答案给 RR(q=1) 的完成时间为 "P1=17、P2=12、P3=6、P4=16"（本笔记的 P3=6、P2=12、P4=16 与其一致；仅 P1 不同）。但本例题总服务时间 ＝ 7+4+1+4 = **16** 个时间单位，而 P1 在 t=0 就已到达，**CPU 从 t=0 起不可能有空闲**，因此**最晚完成的进程不可能晚于 t=16**——"P1=17"在"全程无空闲"的假设下不可能成立，应是参考值笔误。
> 本笔记按约定**逐步推演**（见上表）得出：**P3=6、P2=12、P1=15、P4=16**，平均周转 **9.50**，平均带权周转 **≈2.35**。**答题时必须先写明约定**（新到达 vs 被抢占的入队顺序、时间片从何时起算），约定不同结果会整体平移。

> 【考点延伸·RR 与 SJF 的对比】本例中 SJF/HRRN 平均周转 8.00（最优），RR 平均周转 9.50（较差）——**RR 赢在响应快（P3 到达后 1 个时间单位就被调度，短作业感受不到排队之苦），输在平均周转**（P1 被切成 7 片、反复排队，等到最后才跑完）。

# 2.7 进程同步与互斥

## 2.7.1 临界资源与临界区

**临界资源（Critical Resource）**：**一次仅允许一个进程使用**的资源，例如打印机、共享变量、缓冲区、共享队列……（凡是"共享且必须排他"的，都算）。

**临界区（Critical Section）**：访问临界资源的**那一段代码**。注意：**临界资源是"资源"，临界区是"代码"**，两个概念要分清。

访问临界区一般被规范成四个部分：

![2-16 临界区访问的四个部分](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-16_critical_section.png)

*图2-16 访问临界区的四部分：进入区（检查+上锁）→ 临界区（访问共享资源）→ 退出区（开锁）→ 剩余区（其他代码）。*

| 部分 | 作用 |
| --- | --- |
| **进入区** | 检查是否可以进入；若可以则"上锁"（设置标志）——**实现互斥的关键** |
| **临界区** | 访问临界资源的那段代码（同一时刻**只允许一个进程**待在这里） |
| **退出区** | "开锁"（清除标志），释放资源 |
| **剩余区** | 与临界资源无关的其他代码，任意时刻可执行 |

## 2.7.2 同步 vs 互斥（两大种制约关系）

| 概念 | 制约类型 | 含义 | 例子 |
| --- | --- | --- | --- |
| **同步（直接制约）** | **时序**关系 | 两个进程的执行有**先后顺序**；后者的操作依赖前者 | A 先放数据，B 才能取数据；谁先谁后是"约定" |
| **互斥（间接制约）** | **排他**关系 | 竞争同一临界资源（只能轮流用） | A、B 都要用同一台打印机 |

> 【记忆口诀】**同步=先来后到（时序），互斥=独享排他（占用）。** 做题先分辨："它们之间是'必须一方等另一方'（同步），还是'不能同时用某资源'（互斥）？"

## 2.7.3 互斥的四个基本原则

1. **空闲让进**：临界区空闲时，应允许一个进程进入；
2. **忙则等待**：已有进程在临界区时，其他进程必须等待；
3. **有限等待**：等待时间有限，不能永远等不到（**防饥饿**）；
4. **让权等待**：进不去临界区的进程**应放弃 CPU**（不能"忙等"空转浪费 CPU）。

> 【考点】四个原则依次对应四个"坑"：① 空闲让进——单标志法的缺陷；② 忙则等待——双标志先检查法的缺陷；③ 有限等待——优先级调度的饥饿；④ 让权等待——**Peterson、TSL、Swap 都不满足（都是忙等）**，只有**信号量/管程**等"唤醒-阻塞"机制满足。

## 2.7.4 软件方法：逐个剖析缺陷

设两个进程 P0、P1，共享变量：

- **flag[i] = true 表示"进程 i 想进"**（自己的意愿）；
- **turn = j 表示"该轮到 j 了"**（谁谦让）。

### (1) 单标志法（turn 变量）

```c
P0: while(turn != 0) ;     // 轮到我了吗？
    进入临界区;             // 访问共享资源
    turn = 1;              // 走之前把"机会"交给1号
P1: while(turn != 1) ;
    进入临界区;
    turn = 0;
```

- **能保证互斥**（两个进程轮流交替进入）。
- **缺陷：违背"空闲让进"**。如果 P0 跑完后把 turn=1，而 P1 此刻根本**不想进**（在剩余区做别的），P0 再想进也只能干等——**"空闲"却进不去**。强制"轮流"，效率低。

### (2) 双标志先检查法（flag[]，先检查后置位）

```c
P0: while(flag[1]) ;       // ① 检查对方是否想进
    flag[0] = true;        // ② 声明"我想进"
    进入临界区;
    flag[0] = false;       // ③ 退出声明
P1: while(flag[0]) ;
    flag[1] = true;
    进入临界区;
    flag[1] = false;
```

- 想进就能进（满足空闲让进）；**缺陷：违反"忙则等待"**——检查（①）与置位（②）之间有瞬间间隔：P0 检查发现 flag[1]=false，还没设 flag[0]=true 时，P1 检查发现 flag[0]=false → **双方都以为对方没想进 → 同时进入临界区！**（违背互斥）

### (3) 双标志后检查法（flag[]，先置位后检查）

```c
P0: flag[0] = true;        // ① 先声明"我想进"
    while(flag[1]) ;       // ② 再检查对方
    进入临界区;
    flag[0] = false;
P1: flag[1] = true;
    while(flag[0]) ;
    进入临界区;
    flag[1] = false;
```

- 能保证互斥；**缺陷：违反"空闲让进"**——P0、P1 同时置位后，**都**看到对方想进 → **两个都在 while 里死等 → 谁都不进去 → 相当于死锁**。

### (4) Peterson 算法（"主动争取 + 谦让 + 最后检查"）⭐

![2-17 Peterson 算法](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-17_peterson.png)

*图2-17 Peterson：先写"我想进"（flag），再写"让给你"（turn），最后检查"对方也想进且对方更优先（turn在后写者手中）"就等——后写 turn 者胜出。*

```c
P0: flag[0] = true;      // ①主动争取：把“我想进”写在门口
    turn = 1;            // ②谦让：把机会让给对方（1号）
    while(flag[1] && turn==1);  // ③检查：对方也想进且机会在对方→等
    // ——临界区—— 使用临界资源
    flag[0] = false;     // ④退出：撤销“我想进”，让对方进

P1: flag[1] = true;      // ①主动争取
    turn = 0;            // ②谦让
    while(flag[0] && turn==0);  // ③检查
    // ——临界区—— 使用临界资源
    flag[1] = false;     // ④退出
```

**三个思想**：① 主动争取——`flag[i]=true`，告诉别人"我想进"；② 谦让——`turn=对方`，把"优先权"让出去；③ 最后检查——`while(flag[对方] && turn==对方)`，**check 对方是否也想进、且最后写的 turn 属于谁**。

**为什么能互斥？** 若双方同时"谦让"（都写了 turn），**最后一个写 turn 的人先让（wait），另一个先通过**——"后写者胜出"，保证**至多一个**通过检查，不可能同时进入临界区。

**满足**：互斥、空闲让进、**有限等待**；**不满足**：**让权等待（忙等）**。

> 【易错】① flag 表示"自己想不想进"（各自只改自己的）；② turn 表示"最后谁谦让"（后写者让先）；③ **顺序"先写 flag，再写 turn"不能反**——反了就成"双标志后检查法"了。④ Peterson 只适用于**两个进程**互斥。

## 2.7.5 硬件方法

| 方法 | 原理 | 特点 |
| --- | --- | --- |
| **中断屏蔽** | 进入临界区前关中断，退出后开中断，中断一关就不可能被切换（单 CPU 保证原子性） | 简单高效，但**只能用于单处理机**；关中断时间过长影响系统响应 |
| **TestAndSet（TSL）** | 一条**原子指令**：`return old; set lock=true;`——读旧值并同时置位 | 硬件保证"读+写"原子；**忙等**，多处理机可行 |
| **Swap/XCHG** | 原子交换指令：把 `key=1` 与锁变量交换；若换回来的旧值是 1 说明有人在用 | 同 TSL；**忙等** |

> 【考点】以上硬件方法**都不能解决"让权等待"**（都是 while 忙等）。要"让权"，必须用**信号量/管程**的"阻塞-唤醒"机制。**TSL/Swap 适合多核**；**关中断仅适合单核**。

#### 深化学习：TSL / Swap 为什么"天生原子"

软件方法翻车的根源只有一个：**"检查"和"上锁"是两条指令，中间能被人插队**。硬件方法把两件事焊死在一条指令里：

![2-33 TSL 与 Swap 的原子性](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-33_hardware_sync.png)

*图2-33 TSL：读旧值 + 置 1 一条指令完成（配合总线封锁，其他核插不进来）；Swap：一次交换后看换出的旧值判断是否抢到锁。*

**图后解读要点**：

- **TSL 的两步在一条指令内完成**：`(RX)=(LOCK); (LOCK)=1`——即使多核并发执行，硬件（缓存一致性/总线锁）保证这一读一写之间**没有任何指令能插进来**；
- **Swap 是 TSL 的"变体"**：把随身带的 1 换进去、把旧值换出来看——本质同样是"读+写"一步走；
- 【易错】TSL/Swap 只是**进入区**的原子化，**退出区（清锁）和临界区本身还要自己写**；它们依旧"忙等"（自旋消耗 CPU），所以**不满足让权等待**；
- 【判断题句式】"TSL 指令执行期间可以被中断打断" → **错**（原子指令不可分割；且它常配合关中断/总线锁实现）。

## 2.7.6 信号量机制（Semaphore）——PV 原语

### 从整型信号量到记录型信号量

**整型信号量（经典在考纲）**：只有一个整型 `S`，P 操作 `while(S<=0); S--;`，V 操作 `S++`。
**缺陷**：`while(S<=0)` 是**忙等**——违反**让权等待**！改进后得**记录型信号量**：

![2-18 记录型信号量与 P/V 流程](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-18_semaphore_pv.png)

*图2-18 记录型信号量 = value（整型）+ 等待队列 L。P：先减，<0 则阻塞入队；V：先加，≤0 则唤醒队首一个进程。*

**记录型信号量结构**：

```c
typedef struct {
    int value;          // 资源计数
    struct PCB *L;      // 等待队列（存放阻塞在本信号量上的进程）
} semaphore;
```

**P 操作（申请资源，S.value--）**：
```
S.value = S.value - 1;
if (S.value < 0) 阻塞该进程，放入 S.L 等待队列（主动让出 CPU = 让权等待）；
```

**V 操作（释放资源，S.value++）**：
```
S.value = S.value + 1;
if (S.value <= 0) 从 S.L 队列唤醒一个进程，改为就绪态；
```

**value 的物理意义（会算题）**：

| value | 含义 |
| --- | --- |
| value ≥ 0 | 剩余**可用**资源数量 |
| value < 0 | **绝对值 = 正在等待的进程数** |

例：S=2 → 还有 2 个资源；S=0 → 没资源、也没人等；S=−3 → 3 个进程排队等待。

> 【考点】① P 和 V 都是**原子操作**（原语，关中断实现）；② **P 可能阻塞，V 一定不会阻塞**（V 只会唤醒别人）；③ **P/S 成对出现**：用一次资源必有对应一次释放；④ **V 可以由别的进程执行**（唤醒者：如消费者唤醒生产者）。

#### 专项训练：手把手算一遍信号量的值

选择题最爱"给操作序列求 S 的值和等待进程数"，照下面这张表推就行：

![2-34 信号量取值追踪实例](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-34_semaphore_trace.png)

*图2-34 S 初值=2 时的逐步追踪：P 减 V 增；S<0 的绝对值 = 等待队列长度；V 触发唤醒但被唤醒者要重新排队等调度。*

**推演规则（背三句）**：

1. **P(S)**：S 先减 1；减完 **< 0 → 自己阻塞入队**；**≥ 0 → 继续跑**；
2. **V(S)**：S 先加 1；加完 **≤ 0 → 说明还有人在等，唤醒队首一个**（被唤醒者进就绪队列，**不是马上运行**）；**> 0 → 没人等，什么都不做**；
3. **|S|（S<0 时）永远等于当前排队人数**——看到负数直接数绝对值。

**例（自测）**：S 初值 = 3，经过 4 次 P、1 次 V 后，S = ？有几个进程在等？
**解**：3 −4 +1 = **0**，S=0 ≥ 0 → **无人等待**（资源刚好用完但没人排队）。

### 信号量三大用法（解题三板斧）

| 用法 | 初值 | 写法 | 用途 |
| --- | --- | --- | --- |
| ① **互斥信号量** | **1** | 每个进程 `P(mutex); 临界区; V(mutex);` | 实现互斥：同一时刻只有一个进程进临界区（资源只有 1 份） |
| ② **同步信号量** | **0** | 前面进程 `V(sync);`，后面进程 `P(sync);`（**前 V 后 P**） | 实现先后次序：**先者 V、后者才能 P 通过，否则后者阻塞**（有时效的必然性） |
| ③ **资源计数信号量** | **N** | 每个进程 P 一下 / V 一下 | N 个同类资源（缓冲区空位、可用槽位）；S<0 时 |S| 就是等的人数 |

> 【记忆口诀】**"互斥 1、同步 0、资源 N；先资源、后互斥；前 V 后 P。"**

## 2.7.7 前驱图 → 信号量（真题必考题型）

![2-19 前驱图到信号量实现](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-19_precedence_graph.png)

*图2-19 左侧前驱图（S1 → S2、S3 → S4 → S5），右侧为对应 PV 实现："每条边 = 一个初值 0 的同步信号量；前驱 V、后继 P"。*

**三步模板**：① 每条有向边设一个**初值为 0** 的同步信号量（s12, s13, s24, s34, s45）；② 前驱进程在**所有任务都完成后**，对每条出边各 V 一次（后 V）；③ 后继进程**一开始依次**对每条入边各 P 一次（前 P）。

```
semaphore s12=0, s13=0, s24=0, s34=0, s45=0;

S1  { S1;  V(s12); V(s13); }    // 完成任务才V（后V）
S2  { P(s12); S2;  V(s24); }    // 先P入边信号量（前P）
S3  { P(s13); S3;  V(s34); }
S4  { P(s24); P(s34); S4;  V(s45); }   // 两条入边 → 两个P
S5  { P(s45); S5; }
```

> 【口诀】**"入边几条 P 几个，出边几条 V 几个；先 P 后执行，执行完再 V。"**

## 2.7.8 管程（Monitor）

信号量的问题：P/V 分散在各个进程的代码里，写错顺序（如图 2-20 的死锁）很难查。**管程**的思路：把"共享资源 + 对它的操作 + 初始化"**封装**成一个模块，**互斥由编译器自动保证**（一次只有一个进程能进入管程），程序员不用手写锁：

![2-20 管程结构](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-23_monitor.png)

*图2-20 管程 = 共享数据结构 + 一组操作过程 + 初始化代码；条件变量支持内部 wait/signal。*

**管程特性**：
1. 一次仅允许**一个进程**进入管程（互斥自动保证，相当于一个"房间"）；
2. 想进管程必须排队（**入口等待队列**）；
3. **条件变量（condition variable）**，支持两个操作：
   - `x.wait()`：释放管程（让别的进程能进）、把自己挂到 x 的等待队列；
   - `x.signal()`：唤醒 x 队列中的**一个**进程（或广播）；
4. **条件变量没有值**，只有等待队列（与信号量不同！）；signal 后若无等待者，什么也不做。

> 【考点对比】**信号量**：同步代码分散在多个进程中，灵活但易错、易死锁；**管程**：封装成"类"，互斥由编译系统保证，安全性好，但不如信号量灵活。**管程由编译器实现，信号量由 OS 原语实现**。408 大纲对管程主要考概念（判断/选择），PV 大题一般仍用信号量作答。

## 2.7.9 经典同步问题（三大题，PV 必须会默写）

### ① 生产者-消费者问题

**问题描述**：生产者往缓冲区放产品；消费者从缓冲区取产品。缓冲区容量 N。empty = 空闲槽位数、full = 产品数、mutex = 缓冲区互斥锁。

![2-21 生产者-消费者（N缓冲）](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-20_producer_consumer.png)

*图2-21 N 缓冲版：P(empty)/V(full) 是"资源"同步信号量，P(mutex)/V(mutex) 是"互斥"信号量。顺序必须是"先资源、后互斥"。*

```c
semaphore mutex = 1;      // 互斥信号量：实现缓冲区的互斥访问
semaphore empty = N;      // 资源信号量：剩余空闲槽位（初值=缓冲区容量）
semaphore full  = 0;      // 资源信号量：已经放好的产品数（初值0）

// 生产者
while(1){
    P(empty);             // ① 先P资源信号量：要一个空位（没有空位就阻塞）
    P(mutex);             // ② 再P互斥信号量：独占缓冲区（防止两生产者同抢一个空位）
    把产品放入缓冲区;       // ③ 临界区
    V(mutex);             // ④ 开锁。注意：V的顺序可以互换（先开锁再V(full)也行）
    V(full);              // ⑤ 通知消费者：多了一个产品
}
// 消费者
while(1){
    P(full);              // ① 先P资源信号量：要有产品（没有产品就阻塞）
    P(mutex);             // ② 再P互斥信号量：独占缓冲区
    从缓冲区取出产品;
    V(mutex);             // ③ 开锁
    V(empty);             // ④ 通知生产者：空出一个位置
    消费产品;              // ⑤ 使用产品（对产品的"使用"不在临界区内！）
}
```

**单缓冲版（N=1）**：`empty=1, full=0, mutex=1`——代码完全一样，只是缓冲区大小变成 1。**即使只有 1 个槽，"同步 + 互斥"两个信号量也都是必需的**（empty 保证不会同时放、full 保证不会同时取；mutex 防止"放与取同时进行"）。

> 【铁律·最大考点】**"先 P 资源信号量（empty/full），再 P 互斥信号量（mutex）"**。若颠倒：
> 生产者 P(mutex) 后卡在 P(empty)（缓冲区满）、消费者 P(full) 后卡在 P(mutex)——**双方互握对方需要的"锁"→ 死锁！**

### ② 读者-写者问题

**问题描述**：共享文件（或数据库）。读写规则：**读-读可并行；读-写互斥；写-写互斥**。读者优先版（经典）：

![2-22 读者-写者（读优先）](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-21_readers_writers.png)

*图2-22 读优先版："第一个读者负责锁 rw、最后一个读者负责开锁"，中间读者只加计数。*

```c
semaphore rw = 1;         // 读/写互斥信号量（"文件大门"）
semaphore rc_mutex = 1;   // 保护 count 的互斥信号量
int count = 0;            // 当前正在读的读者数

// 读者
while(1){
    P(rc_mutex);                      // ① 先保护 count（防止两个读者同时改 count）
    if(count == 0) P(rw);             // ② 第一个读者：锁住文件大门（写者也进不来）
    count++;                          // ③ 读者计数+1（后面的读者：只加计数，不再动 rw）
    V(rc_mutex);                      // ④ 释放 count 锁
    读文件;                            // ⑤ 读-读并行（都没动 rw）
    P(rc_mutex);
    count--;                          // ⑥ 读完：计数-1
    if(count == 0) V(rw);             // ⑦ 最后一个读者：打开大门（让写者/新读者进）
    V(rc_mutex);
}
// 写者
while(1){
    P(rw);                            // ① 申请"文件大门"（与所有读者+写者互斥）
    写文件;                            // ② 只有一个写者在此（读/写都进不来）
    V(rw);                            // ③ 释放
}
```

**要点**：
- **"第一个读者上锁、最后一个读者开锁"**——一个 rw 信号量就把"读-写互斥、写-写互斥"全部搞定，而**读者之间可以同时读**（因为只有第一个和最后一个读者动 rw）。
- 若把 `if(count==0) P(rw)` 这一句去掉（或写成每个读者都 P(rw)）→ 读者之间也互斥了，退化成"读写全互斥"——**常见的错误写法**。
- **写优先思路（一句话）**：再加一个信号量 `w`；写者先 `P(w)`，读者进入前也先 `P(w)`——只要有一个写者在等，新读者就被挡在门外，等现有读者读完、写者写完；否则**读者源源不断时写者会"饿死"**（读优先的代价）。

#### 深化学习：读优先为什么会"饿死写者"，w 闸门怎么救

![2-35 写优先补丁](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-35_writer_priority.png)

*图2-35 读优先的时间线推演：读者 A→B→C→D 一个接一个，写者 W 一直卡在 P(rw)；右侧给出"加 w 闸门"的写优先代码。*

**时间线对照（先复现问题，再看补丁）**：

- **读优先版的病根**：`if(count==0) P(rw)` —— 只要 count 从不到 0（读者一个接一个），rw 就**永不释放**，写者在 P(rw) 上无限等待；
- **w 闸门的工作原理**：写者到达先 `P(w)` 占住闸门 → 后续读者卡在 `P(w)` → 现有读者读完 count 归 0 释放 rw → **写者拿到 rw 开写** → 写完 `V(w)` 放行。写者最多等"已在读的那批人"，不会被新读者无限插队；
- 【考点】三个信号量各司其职要能一句话说清：**rw = 读写互斥；rc_mutex = 保护 count 计数；w = 写者的"排队闸门"**；
- 【延伸·读写公平法】考试若问"既不让写者饿死、也不让读者饿死"的方案，答：**排队站队法（公平法）**——读写都先在 w 上排队（FIFO），谁先到谁先进，兼顾双方。

### ③ 哲学家进餐问题

**描述**：5 个哲学家围坐圆桌，中间一盆饭；每人左右各一根筷子；哲学家：思考 → 拿起**左**筷 → 拿起**右**筷 → 进餐 → 放下。若 5 人**同时**拿起左筷 → 每人占一根、都等另一根 → **循环等待 → 死锁**！

![2-23 哲学家进餐](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-22_philosophers.png)

*图2-23 哲学家进餐：死锁推演与三种解法（限4人/奇偶分序/一次性申请）。*

**三种解法（只需掌握前两种的代码，第三种一句话解释）**：

| 解法 | 思想 | 破坏了的条件 | 代码要点 |
| --- | --- | --- | --- |
| ① **最多 4 人同时进餐** | 设 `semaphore num = 4;` 进餐前 P(num)，吃完 V(num) | 破坏"循环等待"形成的可能（总有 1 人能吃完） | `P(num); P(左); P(右); 吃; V(右); V(左); V(num);` |
| ② **奇数先左、偶数先右**（或规定"先拿编号小的"） | i 为奇数先拿**左**、i 为偶数先拿**右** | 破坏"循环等待"：0、2 先抢右，1、3 先抢左，**顺序不一致，环被打断** | `if(i%2==0){ P(右); P(左); } else { P(左); P(右); }` 放筷顺序反过来 |
| ③ **一次性申请两根** | 用互斥信号量包住"拿左+拿右"（等价 AND 型信号量）：`P(mutex); P(左); P(右); V(mutex);` | 破坏"**请求并保持**"——等的时候手上没筷子 | 代价：拿筷子被串行化，效率下降 |

**注意**：放筷子用 V(rw) 之类的代码必须与拿筷子顺序相反（`V(右); V(左);`）——**先放后拿、后拿先放**。

> 【考点】哲学家问题是**死锁必要条件**的绝佳案例（互斥、不剥夺、请求并保持、循环等待四者齐备）——所以设计解法要么破坏"请求并保持"，要么破坏"循环等待"，**互斥（筷子）无法破坏**。

### ④ 吸烟者问题（"按资源分组"的生产者-消费者）

**描述**：供应者轮流把"三种材料（烟草、纸、胶）中的两种"放上一张桌子；三名吸烟者**各自永久持有一种材料**，谁缺的两种出现在桌上，谁就能卷烟抽。抽完后供应者再放下一组。

![2-39 吸烟者问题](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-39_smokers.png)

*图2-39 吸烟者问题：供应者按"资源组合"分组唤醒——放哪两种，就 V 哪个 offer。*

```c
semaphore offerA=0, offerB=0, offerC=0, finish=0;

供应者:
while(1){
    随机取两种材料放桌上;
    if(桌上是 烟草+纸)   V(offerC);   // 只唤醒持有胶的C
    else if(桌上是 烟草+胶) V(offerB); // 唤醒持有纸的B
    else                 V(offerA);   // 唤醒持有烟草的A
    P(finish);                        // 等他抽完再放下一组
}
吸烟者i(i = A/B/C, 对应 offer_i):
while(1){
    P(offer_i);          // 等属于自己的组合出现
    取走材料; 卷烟; 抽掉;
    V(finish);           // 通知供应者：桌面空了
}
```

**为什么值得学**：它是"**一对多、按资源种类分发**"的生产者-消费者——三种材料组合对应三个同步信号量（初值全 0），一次**只 V 一个**（一组材料只可能唤醒一个人）。考试变形：把"两种材料"换成"一类消息"、把吸烟者换成"三类处理进程"，骨架完全一样。

### ⑤ 睡眠理发师问题（有限的等待队列）

**描述**：理发店 1 名理发师、1 把理发椅、**n 个等候座位**。顾客有空位就取号等候，满员直接离开；理发师没客时睡觉。

![2-40 睡眠理发师问题](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-40_barber.png)

*图2-40 睡眠理发师：waiting 计数 + 互斥保护 + 两个同步信号量（customers/barber）。*

```c
semaphore customers=0, barber=0, mutex=1;
int waiting = 0;                      // 正在等候的顾客数（共享变量！）

理发师:
while(1){
    P(customers);                     // 没顾客 → 睡觉
    P(mutex);
    waiting--;                        // 叫一号
    V(barber);                        // 发"可以理了"的号
    V(mutex);
    理发;
}
顾客:
while(1){
    P(mutex);
    if(waiting < n){                  // 有空位（判断和修改都在锁内！）
        waiting++;
        V(customers);                 // 报到（可能叫醒睡觉的理发师）
        V(mutex);
        P(barber);                    // 等叫号（没轮到就等）
        理发;
    } else {
        V(mutex);
        离开;                          // 满员即走，不再等
    }
}
```

**两个必抓的易错点**：① `waiting` 是共享变量，**读判断和增减都必须在 mutex 内**——漏锁是本题第一大坑；② 满员分支用 **if 直接离开**，绝不能再 `P(barber)` 排队——否则"满员走人"变成"满员傻等"，题意全变。

> 【考点谱系】生产者-消费者（单/多缓冲）→ 读者-写者（计数+互斥）→ 哲学家（死锁避免）→ 吸烟者（按组分发）→ 理发师（有限队列）——五大经典覆盖了 PV 大题的全部骨架，出题人只能在其上换皮。

## 2.7.10 【必做】多类合作进程综合 PV 例题

**解题"四步法"（写进答卷的骨架）**：

1. **找同步关系**：谁必须先于谁？（前驱关系 → 同步信号量，初值 0，前 V 后 P）
2. **找互斥关系**：哪个资源同时只能一人用？（→ mutex，初值 1）
3. **设信号量**：命名、初值、含义（每个都要说明！如 `empty=N` 表示空闲槽位数）
4. **写代码**：进程 = 若干"P-工作-V"段；**先资源后互斥**；一个进程多个同步关系时按前驱顺序排 P。

### 综合例 1：三进程"流水线"（两个单缓冲接力）

**题目**：进程 A 产生数据存入缓冲区 B1（容量 1）；进程 B 从 B1 取走数据、加工后存入缓冲区 B2（容量 1）；进程 C 从 B2 取出数据输出。用信号量写出三个进程的 PV 代码。

**四步法求解**：

- ① 同步关系：A 先放 B1 → B 才能取（B1 里"有数据"）；B 取走后 A 才能再放（B1 "空"）；同理由 B→B2→C。
- ② 互斥关系：**B1、B2 容量都为 1，且每端只有 1 个进程**——"放"与"取"不可能同时（一个进程放完另一个才取？不对——放和取是不同进程，同时访问 B1 危险！）……等等：B1 只有一个位置，A 放、B 取是**两个不同进程**，若无互斥，A 正在放的数据与 B 正在取的数据可能交错。但容量为 1 时，`empty1` 与 `full1` 两个同步信号量已经隐含互斥：A 必须等 B 取走才能放，B 必须等 A 放好才能取——**同一时刻只有一个进程操作 B1**。所以容量 1 + 单生产者单消费者：**不需要额外 mutex**。
- ③ 信号量：`empty1=1`（B1 空位）、`full1=0`（B1 有货）、`empty2=1`、`full2=0`。
- ④ 代码：

```c
semaphore empty1=1, full1=0, empty2=1, full2=0;

A 进程:
while(1){
    生产数据;
    P(empty1);            // 要一个B1的空位（等B取走上一个）
    数据放入B1;
    V(full1);             // 通知B：B1有货了
}
B 进程:
while(1){
    P(full1);             // 等B1有货（被A唤醒）
    从B1取走数据;
    V(empty1);            // 告诉A：B1空了，可再放（唤醒A）
    加工数据;
    P(empty2);            // 要一个B2的空位（等C取走上一个）
    数据放入B2;
    V(full2);             // 通知C：B2有货
}
C 进程:
while(1){
    P(full2);             // 等B2有货
    从B2取走数据;
    V(empty2);            // 告诉B：B2空了
    输出数据;
}
```

**易错点**：① 四个信号量初值：`empty=1`（可放）与其配对的 `full=0`（没货）——**每对"空/满"同步信号量初值为 1/0**；② B 进程里有**两组**"P-工作-V"（对 B1 一组、对 B2 一组），**不能把两个 P 连在一起写**：`P(full1); P(empty2); 取; 放; ...` 也会死锁（若 B1 有货而 B2 满，B 会握住 B1 的货不放）——**正确写法是"取完立刻 V(empty1)，放之前再 P(empty2)"**，与生产者-消费者的"先资源后互斥"思想同源。

### 综合例 2："爸爸/妈妈/儿子/女儿"（含互斥的两组生产者+两组消费者）

**题目**：桌上放一个盘子，**每次只能放一个水果**。爸爸专门放**苹果**，妈妈专门放**橘子**；女儿专吃**苹果**，儿子专吃**橘子**。盘子空时爸爸/妈妈才能放；有苹果时女儿取，有橘子时儿子取。用信号量实现。

**四步法**：

- ① 同步关系：放了苹果→女儿才能取（apple 信号量）；放了橘子→儿子才能取（orange）；被取走后→盘子空了，爸爸/妈妈才能放（plate 信号量）。
- ② 互斥关系：盘子同一时刻只能一个人动。但注意到：**盘子容量 1 时，plate 信号量（初值 1）本身就实现了互斥**（放和取必然互斥：有人放着/占着，别人就 P 不到）。这是与"生产者-消费者"的对照：**容量 1 且没有"多者对同一侧"时，空位信号量可兼任互斥锁**。严谨起见，也可再加一个 `mutex=1` 包住对盘子的操作（写了也不扣分，**不写也对——因为主体本来就是同一个信号量**）。
- ③ 信号量：`plate=1`（盘子空/可用）、`apple=0`、`orange=0`。
- ④ 代码：

```c
semaphore plate=1, apple=0, orange=0;

爸爸:
while(1){
    P(plate);             // 等盘子空
    放苹果;                // 放的动作（本身满足互斥）
    V(apple);             // 通知女儿
}
妈妈:
while(1){
    P(plate);             // 等盘子空
    放橘子;
    V(orange);            // 通知儿子
}
女儿:
while(1){
    P(apple);             // 等有苹果（沉睡直到爸爸放）
    取苹果;
    V(plate);             // 盘子空出一个位置
    吃苹果;                // 用/吃苹果不是临界资源，可在V之后做
}
儿子:
while(1){
    P(orange);
    取橘子;
    V(plate);
    吃橘子;
}
```

**拓展（真题常改）**：若盘子能放 **N（如 2）个**水果——`plate = N`，其余不变；若要求"盘子中**要么全是苹果、要么全是橘子**"，则需引入互斥信号量（放水果前 P(mutex) 检查种类），属于信号量互斥+同步的复合问题。

> 【易错】① 取水果的进程也要 `V(plate)`（取走=腾出空位）；② "吃苹果"放在 `V(plate)` 之后，**不要把吃水果放临界区**——吃不属于盘子的占用；③ 若盘子容量 1 而去掉 plate 信号量，会出现"爸爸放的时候妈妈也在放"（两个水果挤一个盘子）——**容量为 1 也不能省第一个信号量**。

# 2.8 死锁（Deadlock）

## 2.8.1 什么是死锁

**死锁**：多个进程因竞争资源而**互相等待**，每个进程都占着一些资源不释放，又都在等别的进程释放——**没有外力（OS 干预）谁也无法推进**，全体"卡死"。

比喻：四人打牌，每人欠另一个人 100 块钱，谁也不先还——**谁都不动，无限循环**。

## 2.8.2 死锁 vs 饥饿 vs 死循环（极易混）

| 概念 | 谁的问题 | 是否占用 CPU | 能否靠等待解决 |
| --- | --- | --- | --- |
| **死锁** | 多个进程**相互**等待（环） | **不占 CPU**（都阻塞了） | 不能，必须 OS 干预（剥夺/撤销） |
| **饥饿** | 一个进程**一直**等不到资源（调度器不公平，如低优先级） | **不占 CPU**（也在等） | 理论上会轮到（用"老化"可缓解），也可能永远饿着 |
| **死循环** | 进程自身 bug（while(1) 空转） | **占着 CPU 空转** | 与资源无关，系统不用管它别的进程照常运行 |

> 【考点】**死锁与饥饿都"不在 CPU 上"；死循环"在 CPU 上"**。死锁是"等别人"（环），饥饿是"等自己/被歧视"（无环），死循环是自己空转。

#### 深化学习：死锁 vs 饥饿的一图对照

![2-38 死锁与饥饿的对照](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-38_deadlock_vs_starvation.png)

*图2-38 左：P1 持 R1 等 R2、P2 持 R2 等 R1——循环等待，双方冻结；右：优先级调度下 P3 长期抢不过 P1/P2——系统仍在推进，只有 P3 受害。*

**图后解读要点（判断题的三个抓手）**：

- **看系统是否还在推进**：死锁区域"整体冻结"（涉及的那几个进程全都停摆）；饥饿时**其他进程照常运行**，只有受害者一人排队排到天荒地老；
- **看等的是"谁"**：死锁等的是**彼此手里的资源**（形成环）；饥饿等的是**永远轮不到的调度机会**（无环）；
- **关联前面所学**：SJF 让长作业饥饿、读优先让写者饥饿、静态优先级让低优先级饥饿——**饥饿可以用"老化/公平排队"缓解；死锁只能靠 OS 剥夺/撤销解除**；
- 【易错】"饥饿的进程处于阻塞态，一定占着 CPU" → 前半句对（在等）、后半句错（阻塞不占 CPU）；"死锁进程占着 CPU 互相卡" → 错，死锁进程全都**不占 CPU**（都在阻塞等资源）。

## 2.8.3 死锁的四个必要条件（缺一不可、但**同时满足也可能不死锁**）

![2-24 死锁四必要条件与三类处理策略](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-24_deadlock_conditions.png)

*图2-24 四个必要条件（互斥、不剥夺、请求并保持、循环等待）＋三种处理策略一览。*

| 条件 | 含义 | 生活比喻 | 能否被破坏 |
| --- | --- | --- | --- |
| ① **互斥** | 资源一次只能给一个进程 | 一台打印机同时只能打印一个任务 | **基本不能**（硬件资源的天性）；可用 **SPOOLing 假脱机**"改造"（把独占设备变成共享） |
| ② **不剥夺** | 已获得的资源用完前不能强行拿走 | 手里的奶茶人家不能抢 | 可破坏：**可剥夺**（如内存管理中的页面置换） |
| ③ **请求并保持** | 手里拿着已得的资源，又去申请新资源（边等边占） | 左手拿 A、右手又伸向 B | 可破坏：**一次性全部分配**（要么全给，要么一个不给） |
| ④ **循环等待** | 每个进程都等着下一个进程手里的资源（资源分配图成环） | 四人围圈，每人拿着前一个人的钥匙 | 可破坏：**资源按编号顺序申请**（都从小到大拿，不会成环） |

> 【重点】**四条件是"必要条件"不是"充分条件"**：四个条件同时满足，系统**可能**死锁，但不一定（如资源分配图中虽然有环，但多实例资源下可能无死锁，见 2.8.6）。所以"破坏四条件"只是**预防**手段（静态、保守），要"避免"死锁需用**银行家算法**动态判断。

## 2.8.4 死锁的处理策略（四种，对比背）

| 策略 | 思路 | 适合 | 缺点 |
| --- | --- | --- | --- |
| **预防**（静态） | **破坏四个必要条件之一**：一次性分配（破坏请求并保持）/ 资源可剥夺 / 顺序申请编号（破坏循环等待）/ SPOOLing（软化互斥） | 简单 | 资源利用率低：一次分配很浪费；剥夺有开销 |
| **避免**（动态） | 每次分配前用**银行家算法**判断：给完是否存在**安全序列**，安全才分配 | 中小系统 | 需要知道进程的**最大需求**；不安全状态≠死锁，只是风险 |
| **检测 + 解除** | 定期用**资源分配图**检测；发现死锁后：**撤销进程**（牺牲一部分）/ **资源剥夺** / **进程回退**（恢复到检查点） | 追求可用性 | 事后处理，检测与恢复开销大 |
| **鸵鸟策略** | 不处理——让用户重启（死锁概率极低时最经济） | 简单系统/桌面 OS | 有风险，会"死机" |

【记忆口诀】**"预防破条件，避免算安全，检测再解除，鸵鸟装不看见。"**

## 2.8.5 死锁避免：安全序列、安全状态与银行家算法

**安全状态**：存在一个进程的**安全序列**（如 <P1,P3,...>），按此顺序执行，每个进程所需的资源都能被满足——**安全状态一定不会死锁**。

**不安全状态**：找不到安全序列——**不一定死锁**（可能恰好大家都让一步），但**有死锁风险**。

### 银行家算法（Banker's Algorithm）—— 全过程

比喻：银行家只有 10 万元，贷款的每个客户都声明"我一共需要多少（Max）"，银行家手上剩多少（Available），客户已借多少（Allocation）、还欠多少（Need）。每次放款前，银行家先"假装借出，看看按现有还款计划能不能让所有客户都还完款（安全序列）"——能，才借。

**数据结构**：`Available`（当前空闲资源）、`Max`（每个进程的最大需求量）、`Allocation`（已分配）、`Need = Max − Allocation`。

**分配请求的四步检查**（题目让"判断能否分配"时按这四步）：

1. 请求 ≤ Need（没有超额申请）？否则**错误**；
2. 请求 ≤ Available（现有资源足够）？否则**等待**；
3. **试探分配**：Available' = Available − Request；Alloc' = Alloc + Request；Need' = Need − Request；
4. **安全性检查**：用 Work = Available' 模拟分配，找安全序列；**能找到 → 正式分配；找不到 → 撤销试探，恢复原状，让进程等待**。

![2-25 银行家算法例题](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-26_bankers.png)

*图2-25 银行家算法完整例题：五个进程、三类资源 A/B/C；Need = Max − Allocation；第一问找安全序列，第二问判断 P1 的请求能否满足。*

**【必做例题·固定数据】** 系统有 5 个进程 P0~P4、3 类资源（A, B, C）。已知：

```
Available = (3, 3, 2)

             Max      Allocation     Need = Max - Allocation
P0          (7,5,3)    (0,1,0)           (7,4,3)
P1          (3,2,2)    (2,0,0)           (1,2,2)
P2          (9,0,2)    (3,0,2)           (6,0,0)
P3          (2,2,2)    (2,1,1)           (0,1,1)
P4          (4,3,3)    (0,0,2)           (4,3,1)
```

**第一问：系统是否安全？找安全序列。**

**安全性检查（Work 初始 = Available = (3,3,2)）**：

| 步骤 | 检查 | 分配后回收 | Work 变化 | 说明 |
| --- | --- | --- | --- | --- |
| ① 找 Need ≤ Work 的进程 | **P1 (1,2,2) ≤ (3,3,2)** ✓ | +Alloc(P1)=(2,0,0) | (3,3,2) → **(5,3,2)** | 选 P1（注意不是 P0/P2） |
| ② | **P3 (0,1,1) ≤ (5,3,2)** ✓ | +(2,1,1) | → **(7,4,3)** | |
| ③ | **P4 (4,3,1) ≤ (7,4,3)** ✓ | +(0,0,2) | → **(7,4,5)** | |
| ④ | **P0 (7,4,3) ≤ (7,4,5)** ✓ | +(0,1,0) | → **(7,5,5)** | |
| ⑤ | **P2 (6,0,0) ≤ (7,5,5)** ✓ | +(3,0,2) | → **(10,5,7)** | 全部可完成 |

> **结论：存在安全序列 ⟨P1, P3, P4, P0, P2⟩ → 系统处于安全状态，可以正常分配。**（安全序列**不唯一**：P0 与 P2 之间有的书先 P2；只要"每一步都能找到满足者"即安全。）

**第二问：若此时 P1 请求资源 Request = (1, 0, 2)，能否分配？**

- ① Request ≤ Need(P1)？ (1,0,2) ≤ (1,2,2) ✓
- ② Request ≤ Available？ (1,0,2) ≤ (3,3,2) ✓
- ③ 试探分配：
  - Available' = (3,3,2) − (1,0,2) = **(2,3,0)**
  - Alloc'(P1) = (2,0,0) + (1,0,2) = **(3,0,2)**
  - Need'(P1) = (1,2,2) − (1,0,2) = **(0,2,0)**
- ④ 安全性检查（Work=(2,3,0)）：P1(0,2,0)≤(2,3,0) ✓ → Work=(5,3,2)；P3(0,1,1)≤(5,3,2) ✓ → (7,4,3)；P4(4,3,1)≤(7,4,3) ✓ → (7,4,5)；P0(7,4,3)≤(7,4,5) ✓ → (7,5,5)；P2(6,0,0)≤(7,5,5) ✓ → (10,5,7)。
- **结论：存在安全序列 ⟨P1,P3,P4,P0,P2⟩ → 满足条件，可以分配！**（分配后系统仍安全。）

> 【易错】① 检查顺序：**先看 ≤ Need 再看 ≤ Available**，少一步都要扣分；② **找出安全序列时"这一步还剩哪些进程没满足"要逐个检查**，不能凭感觉；③ **"不安全 ≠ 死锁"**，但"死锁 ⟹ 不安全"；④ Need 是"还需要的最多数量"，不是"这次请求的量"——P1 请求 (1,0,2) 后 Need'(P1)=(0,2,0)，说明 P1 以后最多还要 (0,2,0)。

#### 深化学习：用一道反例彻底分清"不安全"与"死锁"

![2-36 不安全状态未必死锁的反例](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-36_unsafe_no_deadlock.png)

*图2-36 反例：单类资源共 10 个，Available=1，三个进程的 Need 都大于 1——找不到安全序列（不安全）；但没有任何进程真正卡死（未死锁）。*

**反例逐行读**：

- **为什么"不安全"**：Available=1，而 P1 需 5、P2 需 2、P3 需 7——**没有任何一个进程的需求能被立即满足**，无法排出"每步都有人能走完"的安全序列；
- **为什么"没死锁"**：Max 是"**可能**申请的最大量"，不是"必然申请的量"。若 P2 实际只再要 1 个就跑完了，归还 2 个后系统立刻活络——**风险没有兑现**；
- **两种状态的逻辑关系（必背三角）**：安全状态 ⊂ 无死锁；死锁 ⟹ 不安全；不安全 ⟹ 不一定死锁；
- 【考点句式】"银行家算法保证系统不会死锁"——严格说是"保证系统**始终处于安全状态**，从而**避免**死锁"；它不能用于"已经死锁后解除"（那是检测+解除的活）。

## 2.8.6 死锁检测：资源分配图（RAG）与化简

**画法约定**（必背）：
- **圆圈** = 进程；
- **方框** = 资源类，方框内**圆点** = 资源实例（几个点就几个实例）；
- **请求边**：进程 → 资源类方框（"我要一个"，P 方向）；
- **分配边**：**资源实例（圆点）→ 进程**（"我这个给你了"）。

![2-26 资源分配图与化简](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-25_rag.png)

*图2-26 资源分配图：P1、P2、P3 与 R1（2 个实例）、R2、R3。图中虽然有环（P1→R2→P2→R3→P3→R1→P1），但**多实例环 ≠ 死锁**，可完全化简。*

**化简方法（手工化，会画就行）**：
1. 找一个**请求能被满足**的进程（它请求的每一类资源都有空闲实例）；
2. 让该进程**运行完**，**释放它占用的所有资源**（原有的分配边 "撤回"，资源实例数增加）；
3. 重复，直到**所有进程都可化简**（图被完全化简 → 无死锁）。

**例题（图 2-26 左）**：R1 有 2 个实例，1 个给了 P1，**还剩 1 个空闲** → P3 请求 R1 可被满足？

- ① P3 请求 R1：R1 有 1 个空闲实例 → P3 可满足，P3 完成 → 释放它占的 R3；
- ② 收回 R3 → R3 有空闲 → P2 请求 R3 满足 → P2 完成 → 释放 R2 的实例；
- ③ 收回 R2 → P1 请求 R2 满足 → P1 完成；
- ④ 全部进程均可完成 → **图可完全化简 → 系统无死锁**（**尽管图中有环！**）。

**死锁定理（推断题必背）**：

| 情形 | 结论 |
| --- | --- |
| 系统死锁 | ⟺ 资源分配图**不可完全化简** |
| **单实例资源**（每个资源类只有一个圆点） | 图中有环 ⟺ **死锁** |
| **多实例资源** | 图中有环 **不一定** 死锁（如上例） |
| 图中**无环** | **一定没有死锁** |

> 【考点记忆】**"无环必无死锁；单实例有环=死锁；多实例有环≠死锁（要看能不能化简）。"**

**死锁解除**（检测出死锁后的三招）：① **资源剥夺**：强行从某进程手里抢资源给别的进程；② **撤销进程**：终止部分死锁进程（可"一次性全撤"或"逐个撤"直到解除）；③ **进程回退**：让进程回退到某个检查点（要配合检查点机制）。

#### 专项训练：两道化简题判"死"活

![2-37 资源分配图化简两例](/Users/levi/IdeaProjects/操作系统/第2章_进程与线程/figures/ch2-37_rag_simplify_example.png)

*图2-37 例1 可完全化简（无死锁）：P3 无请求边先行完成、释放资源逐个解锁；例2 互持卡死（死锁）：双方请求边互相指，谁的边都抹不掉。*

**化简口诀（按图背）**：**找「要的都给得起」的进程 → 抹边回收 → 循环到无人可化简**。

- **例 1 的关键第一步**：P3 **没有任何请求边** → 它天生"非阻塞"，第一个被化简。考试看到"无请求边的进程"，直接从它开始消；
- **例 2 的判死依据**：P5 要的 R2 全在 P6 手里、P6 要的 R1 全在 P5 手里——**两个进程都阻塞**，化简第一步就卡住 → 不可完全化简 → 死锁，且**死锁进程就是化简后仍连着边的 P5、P6**；
- 【易错】"图中无环或有环"只是**看图**的粗筛；**化简**才是判定死锁的标准流程——多实例资源下"有环但可完全化简 → 无死锁"（见上文例题）；
- 【答题模板】"判断该系统是否死锁"三步：① 画/读资源分配图；② 逐个尝试化简（从无请求边或请求可满足者开始）；③ 下结论——**完全化简=无死锁；剩余节点=死锁进程集**。

## （三）PV 解题方法论（背下来）

> **四步法**：① 找同步关系（谁必须先于谁 → 前 V 后 P，初值 0）；② 找互斥关系（哪个资源只能一人用 → mutex，初值 1）；③ 设信号量（命名+初值+说明含义）；④ 写代码（P-工作-V；**先 P 资源信号量后 P 互斥信号量**；多个 V 顺序可换；把"使用资源"放在 V 之后）。

**三板斧口诀**：互斥 1（初值 1）、同步 0（初值 0）、资源 N（初值 N）；**先资源后互斥；前 V 后 P。**

**代码书写规范**：信号量声明注释含义 → 每个进程 while(1) → 每个 P 写注释（等人的条件）→ 每个 V 写注释（唤醒谁）。

## （四）易错点清单（≥10 条，考前必扫）

1. **程序静态、进程动态**；一个程序可对应**多个**进程。
2. 创建完成后进程进入**就绪**，不是运行；创建时"创建即挂起"是特例。
3. **不存在"阻塞→运行"**（先唤醒回就绪，再调度）；**不存在"就绪→阻塞"**。
4. **"运行→阻塞"是主动的，其余转换基本是被动的**（运行→就绪是被抢占，被动的）。
5. **阻塞与唤醒必须成对**；**切换一定发生在核心态**；撤销父进程要**递归撤销子孙**。
6. **管道是半双工**——双向要两根管道；写满阻塞**写者**、读空阻塞**读者**；读走即删。
7. **线程独有：TID、PC、寄存器组、栈；共享：地址空间、全局变量、堆、打开文件**——**堆共享、栈独有**。
8. **用户级线程切换不需要进核心态**（内核无感知）；**一个 ULT 阻塞 → 整个进程阻塞**。
9. **临界区（代码）≠ 临界资源（资源）**；**普通进程临界区可以调度，只有 OS 内核临界区不能调度**。
10. **互斥四原则**：空闲让进、忙则等待、有限等待、**让权等待**——Peterson/TSL/Swap 都不满足最后一条（忙等）。
11. **必须先 P 资源信号量（空位/产品），再 P 互斥信号量**——顺序反了会死锁；V 的顺序可以互换。
12. **P 可能阻塞，V 绝不阻塞**；value<0 时 |value| = 等待的进程数。
13. **读者-写者："第一个读者 P(rw)、最后一个读者 V(rw)"**——中间读者只动 count。读优先可能饿死写者。
14. **安全状态 ≠ 不会死锁**（安全状态必不死锁）；**不安全状态 ≠ 死锁**（只是可能）。
15. **资源分配图有环：单实例 = 死锁；多实例 ≠ 死锁**（要看能否化简）。
16. 死锁四条件是**必要**而非充分；**互斥**条件最难破坏（用 SPOOLing/RAG 中等）。

## （五）真题风格例题（≥8 道）

**【真题风格 1 · 状态转换】** 下列进程状态转换中，**不可能**发生的是（ ）。
A. 运行 → 就绪　B. 运行 → 阻塞　C. 阻塞 → 就绪　D. 阻塞 → 运行
**答案 D**。阻塞进程必须先被唤醒进入就绪队列，等待调度才能运行。

**【真题风格 2 · 事件序列】** 进程 P 执行 `read()` 系统调用读磁盘，此时 P 的状态变为（ ），当磁盘传输完成（中断处理）后，P 转为（ ）。
**答案：阻塞；就绪**。I/O 是"运行→阻塞"的典型；中断唤醒后是"阻塞→就绪"，不是直接运行。

**【真题风格 3 · 管道】** 关于管道通信，正确的有（ ）。
① 管道由 OS 在内存中管理，读取的数据被删除 ② 管道支持半双工 ③ 管道写满时写进程立即返回 ④ 管道读写需要互斥
**答案：①②④**。③错——写满时写进程被**阻塞**（不是返回）。

**【真题风格 4 · 线程】** 一个进程内创建多个（用户级）线程，哪个说法正确？（ ）
A. 一个线程阻塞，其他线程仍可能运行　B. 线程切换不需要进入核心态　C. 线程之间不能共享全局变量　D. 每个线程都有独立的地址空间
**答案 B**。用户级线程切换在用户态完成；A 错（一个 ULT 阻塞→整个进程阻塞）；C 错（可以共享全局变量）；D 错（共享进程地址空间）。

**【真题风格 5 · 调度计算】** 有 3 个进程：A（到达 0，服务 3）、B（到达 1，服务 5）、C（到达 2，服务 1）。分别用 FCFS 与非抢占 SJF 求平均周转。
**解**：FCFS：A[0,3]、B[3,8]、C[8,9] → 周转 3/7/7 → 平均 5.67。SJF：t=0 只有 A → A[0,3]；t=3 就绪 B(5)、C(1) → 选 C → C[3,4]、B[4,9] → 周转 3/8/2 → 平均 **4.33**（SJF 更优）。

**【真题风格 6 · HRRN】** 就绪队列有两个进程：P1（已等待 2，服务 4）、P2（已等待 5，服务 2），按高响应比优先应选谁？
**解**：响应比 = 1 + 等待/服务。P1 = 1+2/4 = 1.5；P2 = 1+5/2 = 3.5 → 选 **P2**。（P2 服务短且等待久，"性价比"高。）

**【真题风格 7 · PV 补全】** 生产者-消费者（N 缓冲）中，生产者代码 ""处应填：`P(empty); P(mutex); 放产品; V(mutex); ____;`（ ）。
**答案 V(full)**。V 与 P 成对：P(empty) 对应 V(empty)（消费者取后执行），P(full) 对应 V(full)（生产者放后执行）。

**【真题风格 8 · 银行家】** 某系统 Available=(1,1,1)，P0 的 Max=(2,1,1)、Alloc=(1,0,1)，则 Need 为（ ），P0 能否继续申请 (1,0,0)？
**解**：Need = Max − Alloc = (1,1,0)。请求 (1,0,0)：① ≤Need ✓；② ≤Available=(1,1,1) ✓；③ 试探：Available'=(0,1,1)，Alloc'(P0)=(2,0,1)，Need'(P0)=(0,1,0)；④ 若系统中还有另一进程 P1 其 Need=(2,1,2) > Available'，且 P0 完成后释放 (2,0,1) → Available=(2,1,2) → P1 满足 → **安全序列存在 → 可以分配**。（具体结论以完整系统矩阵为准，步骤必须写下。）

**【真题风格 9 · RAG 判断】** 资源分配图中存在一个环（所有资源类都是**单实例**），则系统（ ）。
A. 一定死锁　B. 一定不死锁　C. 可能死锁　D. 无法判断
**答案 A**（死锁定理：单实例资源，环 ⟺ 死锁）。若问"多实例"，答案 C（有环可能死锁）。

**【真题风格 10 · 调度时机辨析】** 下列情形中，**不会**引起立即进程调度的是（ ）。
A. 运行进程阻塞　B. 运行进程时间片用完　C. **处理中断的过程中**　D. 更高优先级进程到达
**答案 C**。中断处理过程中不能调度（关中断执行）。

**【真题风格 11 · PV 追踪】** 信号量 S 初值为 2。当前有 4 个进程依次执行：P1 做 P(S)、P2 做 P(S)、P3 做 P(S)、P4 做 P(S)，随后 P1 执行 V(S)。问最终 S 的值与阻塞在 S 上的进程数。
**解**：逐步推（2→1→0→−1→−2→−1）：P3、P4 在 P(S) 时 S 变负而阻塞；P1 的 V(S) 使 S=−1 并唤醒 P3（进就绪队列，尚未运行）。**最终 S = −1，仍在 S 上排队的进程数 = |−1| = 1 个（P4）**。易错：被唤醒的 P3 已离开 S 的等待队列，不要再算它。

**【真题风格 12 · RR 手算】** 三个进程：P1（到达 0，服务 4）、P2（到达 1，服务 2）、P3（到达 2，服务 3），RR 时间片 q=1，约定"新到达先入队、被抢占后入队"。求完成时间。
**解**：[0,1]P1 → [1,2]P2（t=1 P2 先入队、P1 后入队：[P2,P1]）→ [2,3]P1（t=2 P3 先入队、P2 后入队：[P3,P2,P1]）→ [3,4]P2 完成（完成=4）→ [4,5]P3 → [5,6]P1 → [6,7]P3 → [7,8]P1 完成（完成=8）→ [8,9]P3 完成（完成=9）。完成时间 **P2=4、P1=8、P3=9**；周转 8/3/7。

**【真题风格 13 · 死锁预防措施归类】** 下列方法分别破坏了死锁四个必要条件中的哪一个？① 一次性申请全部资源；② 资源有序分配法；③ SPOOLing 假脱机打印机；④ 可剥夺的进程调度。
**解**：① 破坏"请求并保持"（要么全给、要么不给，等的时候手上没资源）；② 破坏"循环等待"（大家都从小号到大号申请，环闭合不了）；③ 软化"互斥"（把独占设备改造成逻辑共享设备）；④ 破坏"不剥夺"（允许从进程手里抢走资源）。**总结**：互斥最难破坏（SPOOLing 只是"绕开"）；其余三个各有对应破坏手段。

### 参考答案与提示

1. **C**（阻塞态缺的是"事件"，不是 CPU）。
2. **B**（唯一的主动离开运行的边）。
3. **B**（关中断保证原语不被打断）。
4. **C**（写满阻塞写者；A 半双工；B 读走即删；D 必须互斥）。
5. **D**（栈是线程私有现场）。
6. **B**（内核只认进程，ULT 阻塞连坐全进程）。
7. **B**（短作业排在长作业后面干等）。
8. **B**（P1=1+3/6=1.5；P2=1+6/3=3 → 选 P2）。
9. **C**（单实例资源环 ⟺ 死锁；多实例有环未必死锁）。
10. **B**（安全状态必无死锁）。
11. **对**。 12. **错**（PCB 常驻内存，是进程存在的唯一标志）。 13. **错**（V 只会唤醒别人，绝不阻塞）。 14. **错**（多实例下有环未必死锁，要看能否化简）。 15. **错**（切换涉及 PCB、页表基址等内核数据，必须核心态）。
16. FCFS：A[0,5]、B[5,12]、C[12,14]、D[14,18]；周转 5/10/10/13，**平均 9.5**。
17. SJF：A[0,5]；t=5 选最短 C[5,7]；再 D(4)<B(7)：D[7,11]；B[11,18]。周转 5/16/3/6，**平均 7.5**。
18. RR(q=2)：A[0,2]→B[2,4]（t=2 B 先入队、A 后入队）→A[4,6]（t=4 C 先入队、B 后入队）→C[6,8] 完成；t=5 D 到达排入 [C,B,D]，t=6 A 再入队 →B[8,10]→D[10,12]→A[12,13] 完成→B[13,15]→D[15,17] 完成→B[17,19] 完成。完成：A=13、B=19、C=8、D=17；周转 13/17/4/12，**平均 11.5**。
19. 响应比 P1 = 1+3/6 = **1.5**；P2 = 1+6/3 = **3.0** → 选 **P2**。
20. 逐步：2→1→0→1→0→**-1**（此时一个进程阻塞）→0（V 唤醒队首）→**1**。最终 **S=1，无等待进程**。
21. ① Need：P0(1,1,2)、P1(1,1,1)；Work=(1,1,2)：P0√ → Work=(2,1,3) → P1√ → (2,2,3)，安全序列 ⟨P0,P1⟩，**安全**。② (0,1,0)≤Need(P1)√、≤Available√；试探后 Available=(1,0,2)、Alloc(P1)=(0,2,0)、Need(P1)=(1,0,1)；再检：P1√ → (1,2,2) → P0(1,1,2)√ → (2,2,3)，安全 → **可以分配**。
22. 反例（顺序颠倒）：缓冲满时生产者先 P(mutex) 成功、再 P(empty) 阻塞——它**握着缓冲区锁睡觉**；消费者此时要 P(mutex) 才能取货腾位，永远拿不到锁 → 互相等待，死锁。正确顺序保证"拿不到资源时手里没有锁"。
23. 破坏的是**循环等待**。推理：0、2、4 号先伸左手，1、3 号先伸右手——相邻两人中至少有一个"先伸的手"与对方"先伸的手"指向同侧竞争，桌面上总存在"第一步就有空筷子可拿"的人（可证 5 人中必有 1 人两只筷子都空闲），他吃完放下后释放资源，环始终闭合不了。
24. 创建→**就绪**；调度→**运行**；缺页（当前访存指令引发）→ 保持运行态语义上进入内核处理，进程转为**阻塞**等页调入；调入完成（I/O 中断）→**就绪**；调度→**运行**；管道满→**阻塞**（主动等）；读端取走（被唤醒）→**就绪**；时间片到→**运行→就绪**。
25. 第一步找非阻塞进程：P2 的请求 R1 有 1 个空闲实例 → 可满足，P2 完成、释放 R2 → P1 的请求 R2 满足 → P1 完成。**可完全化简 → 无死锁**（注意 R1 的空闲实例是化简的关键——有环不死锁的典型）。
